# 全体アーキテクチャ

この文書では [用語集](terms.md) の言葉を使い、ene のシステム全体を支える実行基盤、4 層の構造、および採用技術の方針をまとめます。
詳しい機能仕様は [対話と音声](features/interaction.md) などの各仕様書に、通信や個別の詳細設計は配下の設計文書に譲り、ここでは全体の見取り図と配置の判断基準を示します。

## 全体構成とホスト・クライアントの境界

ene は常駐するホスト側へ「頭」「手」と「目」の状況選別を、利用者側のクライアント側へ「体」と「目」の状況収集を配置し、4 つの役割を境界で分けて動かします。
常駐ホストが「頭」と状態管理を集約し、PC や将来の各種端末で動くクライアントと `Connect-RPC`（HTTP/2 `h2c` 対応の Protobuf 通信）でつながる構成です。
クライアントは接続時に `端末能力` として画面操作、音声入出力、身体表現などの利用可能な機能を宣言し、ホストは宣言と設定に応じて使う手段やツールを切り替えます。
クライアントの画面はテキスト入出力、設定、承認カードだけに絞り、専用の作業一覧や記憶一覧画面を持たない構成とすることで、端末が増えても対話中心の体験を崩しません。
デスクトップ向けの標準構成ではクライアント本体が UI・音声入出力・知覚を受け持ち、3D アバターを描画する別プロセスのリファレンス実装を標準入出力の JSON Lines IPC で制御します。
毎秒 60 回ほどの頻度で送るリップシンク振幅は応答を待たない一方向通知として扱い、通信の詰まりを起こさずに口パクと再生音声をそろえたうえで、全体のつながりを次の図に示します。

```text
                    +-----------------------------------+
                    |     利用者 / クライアント環境     |
                    +--------+------------------+-------+
          音声入力 / 知覚情報|                  |音声出力 / 表情・動作 / 承認カード
                             v                  |
+-----------------------------------------------+--------------------------------+
| 【クライアント層】（例: デスクトップクライアント＋アバター描画プロセス）         |
|  ・「体」: 姿の描画、表情、JSON Lines IPC による口パク、TTS 再生               |
|  ・「目」（センサー）: 画面・操作状況の収集と通知、音声入出力の仲介            |
|  ・端末能力宣言: 起動・接続時に利用できる機能をホストへ申告                    |
+----------------------------+---------------------------------------------------+
                             | Connect-RPC（Protobuf / HTTP/2 h2c・端末能力・双方向ストリーム）
+----------------------------v---------------------------------------------------+
| 【ホスト層】（常駐ホスト）                                                     |
|                                                                                |
|  +--------------------------------------------------------------------------+  |
|  | 「頭」（ECS 単一イベント駆動ループ）                                     |  |
|  |  ・会話と判断、心の状態の更新、先行 TTS 送出、承認の保留と再開           |  |
|  |  ・自律スケジュール管理、動的ツール登録、自由文ポリシーを含む確認制御    |  |
|  +-----------------------+-----------------------------------+--------------+  |
|                          | 作業セッション / 実行ターン       | 履歴・記憶・設定 |
|                          v                                   v                 |
|  +-----------------------------------+   +----------------------------------+  |
|  | 「手」＆「目」（評価）            |   | 永続化・秘密情報保護             |  |
|  |  ・作業エージェント（MCP/ACP/Wasm）|  |  ・追記型ファイル: 会話ログと要約|  |
|  |  ・作業は対話停止と非結合で実行   |   |  ・組み込み SQLite: 記憶と状態   |  |
|  |  ・「目」の選別（枠組みのみ用意） |   |  ・OS キーチェーン: API キー類   |  |
|  +-----------------------------------+   +----------------------------------+  |
+--------------------------------------------------------------------------------+
```

## 4 層構造と依存ルール

コードベースの依存関係は外側から内側への一方向だけに制限し、純粋なドメイン規則と外部 I/O や描画を切り離しています。

| 層 | 依存できる範囲 | 主な責務 |
| --- | --- | --- |
| L0 純粋ドメイン | 標準ライブラリ、シリアライズ補助、下位の L0 モジュール | 識別子や型定義、安全・権限の判定規則、心と記憶の計算モデル、作業・音声・プラグイン契約 |
| L1 アプリケーション | L0 のみ（外部 I/O はポートトレイト経由） | クライアント共通の進行管理と状態制御（具体的な通信・DB・描画実装を持たない） |
| L2 インフラストラクチャ | L0、L1 のポートトレイト、外部 I/O ライブラリ | 通信契約、DB 永続化、プラグイン実行基盤、3D モデル読み込み、アバター IPC、OS 統合（トレイ、画面取得、ウィンドウ監視） |
| L3 薄いアプリ | L0〜L2 の配線 | プロセス起動、設定と資格情報管理、通信サーバー配線、GUI・アバター描画 |

純粋な状態遷移や判定規則はテストからそのまま検証できるよう L0・L1 へ置き、外部ライブラリや DB・OS との接続実装は L2 へ、起動配線やプロトコル変換・画面描画だけを L3 にとどめます。
構造の崩れを防ぐため、UI からの通信型参照・永続化層からの逆流参照・層をまたぐ禁止依存・クライアント UI 側の `unsafe` コードを自動テストと静的検査で防ぎます。

## ホスト内部の実行基盤とデータ管理

ホストの内部では非同期 I/O 層と ECS による単一のイベント駆動ループを分けて状態を保ちます。
利用者の発話、タイマー発火、知覚通知、「手」からの作業報告はすべて同じ ECS の状態（World）へイベントとして流し、LLM 通信や外部呼び出しの待機で状態管理が競合しない構成です。
永続データは用途ごとに保存先を分け、会話ログと要約は追記型のファイルストアへ記録し、記憶・人格設定・心の状態・設定・スケジュールは WAL モードの組み込み SQLite へ保存します。
記憶の検索には SQLite の FTS5 trigram 全文検索とインメモリで持つ埋め込みベクトルキャッシュを組み合わせ、API キーなどの秘密情報は OS のキーチェーンへ分離して保護します。
「手」が担う `作業セッション` と `実行ターン` は会話ターンから切り離した独立エンティティとして動かし、発話の割り込みや会話の中断が進行中の作業を道連れにしない仕組みです。
外部プロセスを起動する際は OS ごとのプロセスグループや Job Object で束ねて管理し、終了や破棄時に子プロセスが残らないように回収します。
プロンプトは `人格設定` やツール定義などの固定部分と、`心の状態`・想起した `記憶`・最新発話などの可変部分を明確に分けて末尾に差し込むことで、LLM 側の Prefix Cache を保ったまま応答できます。

## 音声・知覚・確認境界・拡張ポイント

音声エンジン・作業ツール・知覚センサー・安全確認の仕組みは、いずれも L0・L1 のドメイン規則や「頭」のイベント駆動ループからトレイトと契約で切り離し、方針の統一と機能追加を両立できる境界として設計しています。
音声対話は STT・LLM・TTS の 3 段パイプラインを基本として文単位で先読み合成を進めて、割り込み時は発話ごとに切り替える世代番号で古い音声を即時破棄し、双方向リアルタイム音声 API は現時点の対象外とする方針です。
操作の安全確認には標準の判定モードと `FullAccess` モードがあり、標準モードでは安全な操作や保存済みの「常に承認」ルールによる自動許可・`自由文ポリシー` を踏まえた LLM 判定・承認カードの 3 段階で大きな作業単位ごとに確認します。
サンドボックスによる実行隔離は実現性を検討中であるため、この 3 段階判定に加え、利用者から会話で得た許可をもとに「頭」が承認を代行する仕組みや `自由文ポリシー` への自動追記を安全境界の基本とした設計です。
「手」の本体は作業実行の制御と報告という最小限の機能だけを持ち、MCP 接続・Wasm プラグイン基盤・外部作業エージェント連携の ACP 契約を通じて作業手段を後から拡張できます。
「目」はクライアントの OS ネイティブ機構で得た状況を選別する枠組みだけを整えて運用しながら調整する前提とし、将来は Tailscale や Cloudflare などの安全な遠隔接続経路もクライアント側のプラグインとして追加する余地を残しています。
各境界の詳しい契約やデータ構造は [ホスト API](api.md)・[心と記憶](design/mind.md)・[作業実行の設計](design/work.md)・[クライアント設計](design/client.md)・[プラグイン拡張](design/plugins.md) を参照してください。

## 採用技術の方針

外部デーモンへの依存を避けつつ各アプリが独立したバイナリで完結するよう、次の技術方針を採用しています。

| 領域 | 主な採用技術 | 役割と選定理由 |
| --- | --- | --- |
| エージェント・非同期実行 | `Rust`、`Tokio`、`Rig` / `Bevy ECS` | ECS ステージによる単一ループ制御と非同期 I/O・LLM 通信を分離する |
| 通信・RPC | `Connect-RPC`（Protobuf / HTTP/2 `h2c`） | 双方向ストリーミングと型付き通信契約をホスト・クライアント間で共有する |
| 会話ログ・永続化 | 追記型ファイルストア、組み込み `SQLite`（WAL・FTS5 trigram） | 会話履歴はファイル追記とし、記憶・状態・設定は外部デーモン不要の単一構成で扱う |
| 秘密情報保護 | OS キーチェーン連携 | 認証情報を OS の資格情報ストアへ隔離して管理する |
| 子プロセス・拡張 | プロセスグループ／Job Object 管理、MCP・Wasm プラグイン基盤・ACP 契約 | 子プロセスの確実な回収と「手」の拡張境界を支える |
| デスクトップ UI・音声・知覚 | `GPUI`、低遅延音声 I/O とリサンプリング、OS ネイティブウィンドウ知覚、`Bevy` ベースの VRM 描画 | GPU 描画のネイティブ UI、低遅延音声処理、透過ウィンドウ上のアバター描画を実現する |

具体的なクレート構成やバージョン固定を確認するときは、リポジトリ直下の `Cargo.toml` を参照してください。
