# Alphaホスト・アーキテクチャ

状態：採用する設計方針（2026-11-03、2026-11-09にホストをRig中心の構成へ書き直し）。**実装済み機能の一覧ではない。** 現在のホストは、1つのヘッドレスRig App、1つのSQLiteドキュメントストア、Connect RPC、心・記憶（語句検索と有限の自動整理）、作業セッション、接続端末の区別と端末操作を持つ。意味検索・埋め込み索引、スケジュール実行、Web検索ツール、音声、ACP/MCP/Wasmアダプター、汎用承認UIは後続である。実装状況と検証の入口は[Alpha計画](alpha.md)、実際の起動方法は[ene-host](../apps/ene-host/README.md)を参照する。

[構想](vision.md)と[機能一覧](features/README.md)を実現するため、旧MVPからホストの中核を検証できるAlphaへ範囲を広げる。旧設計は[履歴](history/mvp-architecture.md)に残す。「長期記憶なし」「作業は一件」「終了後は必ず新規依頼」という旧制約は本設計へ適用しない。

## 1. 決定と非目標

一般的なエージェント機構はRigを利用し、ene固有の実装は、キャラクターの心、作業相手との接続、製品固有の権限とクライアント境界に集中させる。基準は調査時に確認した正式版Rig v0.46.0。実装開始時に正式版・必要API・依存の整合を再確認し、採用版とCargo.lockを固定する。mainへの自動追従や未検証の更新を行わない。[選定根拠](references.md#alpha-rig)

| 領域 | 採用方針 |
| --- | --- |
| 親エージェント | ene固有の人格・ロールプレイと、軽い操作・作業の委譲を担う。一人の親に一つの判断の流れを持たせる |
| 実行管理 | rig-ecsを設計上の基準とし、受信箱、ターン、モデル・ツール呼び出し、停止、保存を利用する |
| 心 | 作者設定、実体験、主観的解釈、現在感情、関係性・成長、表現を区別して連携する |
| 記憶 | 親の即時更新と、確定した記録からの有限の自動整理を併用する |
| 保存・検索 | 心と長期記憶の正本はSQLite。FTS5 trigramとSQLite格納ベクトルのRRF。索引は索引待ち経由で再生成可能。LanceDBは規模・評価に応じた置換候補 |
| 作業相手 | eneの小さな論理APIを内蔵・独自プラグイン・ACP等へ接続する。ACPの全機能を内部へ強制しない |
| ツール・権限 | Rigのツール・Gate・保留・質問を再利用し、一つの認可付きツール実装を直接呼び出しとMCPで共有する |
| ホストAPI | Connect RPCと通知を基本とし、接続経路のアクセス制御とホスト内の操作認可を区別する。保護された入口への移行までは現行のBearer認証を維持する |

ホストへのアクセス制御は、遠隔ではTailscale Serve＋GrantsやCloudflare Tunnel＋Accessなどの既存基盤、ローカルではOSの保護へ委譲する方針とする。クライアント側の接続方式は交換可能とし、ホスト本体に方式ごとのログインや端末トークン管理を重ねない。ただし、信頼できる入口がない状態で認証なしAPIを公開しない。詳細と現行実装との差分は[ホスト接続の設計](design/host-access.md)を正本とする。

報告、相談、軽重、検証や修正の要否は、必要な文脈を持つAIが判断する。場面別の固定行動表や、定期的に意味もなく推論し続けるループは作らない。一つの用事の内部を複数エージェントへ分解するかは子のハーネスに任せ、ene側に汎用の編成基盤を追加しない。

## 2. 構成と所有者

```text
クライアント ─ Connect RPC / 通知 ─ ene-host
                                      │
                             Rigの実行カーネル
                               ├ 親コンパニオン
                               │  ├ 心の参照・更新
                               │  ├ 共通ツール
                               │  └ 作業相手への指示
                               ├ 内蔵の作業相手
                               └ 外部バックエンドの接続

保存：Rigの会話・セッション記録 / SQLiteの心・記憶・設定 / 再生成できる索引
```

ステップ3の実装では、確定した会話の未処理範囲をカーソルで追い、有限のホストワーカーがタスクGrantで整理し、記憶の追加・訂正と処理済み位置を同じSQLiteトランザクションで確定する。FTS5と埋め込みベクトルは索引待ちを介して更新し、正本の所有者・共有範囲・忘却・時刻で検索結果を再検証する。自動想起は入力ごとに最大3件をモデル入力へ入れ、不足時は親の`mind_recall`を使う。専用の第二人格・常設エージェント・汎用ジョブ基盤は追加していない。忘却は想起優先度の低下、共有はcanonicalの`audience`で扱う。

ステップ2の実装では、心と記憶の正本をSQLite（`mind_companions`、`mind_memories`、`mind_operations`）に置き、記憶・現在の心・操作記録を一つのトランザクションで確定する。親のRigエージェントには`mind_recall` / `mind_read` / `mind_update`をホストが束縛したツールとして渡し、所有者・入力出所・操作IDは実行文脈から決める。心ツールを持つのは最初の親一つだけで、子・外部MCPへは公開しない。現在の心はsystem promptの表示用ビューとして渡し、コミット後はターンを止めずに次のモデル呼び出しへ更新する。会話の正本は引き続きRigのセッションログである。自動整理エージェントや第二の実行ループは追加していない。

ホストのRig用ECS Appと、VRMを描画するBevy Appは別である。ホストに描画・音声出力・UIの実行ループを追加しない。将来のクライアントは表示と入力、許可された端末機能を提供する。Slint・アバター描画の既存方針はこの設計変更の対象外とする。

| 状態 | 正本・書込責任 |
| --- | --- |
| 会話・受信箱・内蔵の実行 | Rigの記録と実行主体。eneが同じ寿命管理を重ねない |
| 外部実行 | バックエンドの実行状態と、ホストが受信した受付・結果。未確認は未確認のまま |
| 心・長期記憶 | eneの保存処理。親と自動整理の書込範囲を分ける |
| 設定・許可・秘密情報 | ホスト。秘密情報は通常の記憶・通知・実行ログへ入れない |
| ベクトル・検索索引 | 派生データ。正本の版と共有範囲を確認して利用する |
| UI表示 | 上記から得た表示用状態。UI独自の永続的な感情を持たない |

同じ状態をRigとeneが二重に所有しない。Rigの永続化を現在のSQLite保存へ接続できるかは実装ゲートで確認する。直接の接続に不足があれば公開Store契約等への薄いアダプターを使う。会話全文を別形式で二重保存することを既定にしない。

## 3. 実行と入力

rig-ecsの受信箱と実行カーネルを使い、親一人の判断は直列に管理する。入力の受付、モデル通信、索引更新、子の作業は非同期で進む。親が重い作業の終了をツール内で待ち続ける構造にしない。

RigのSteer（次のモデル呼び出しへ入力）、Queue（現在のターン後へ入力）、Inform（入力だけでは推論を開始しない）を利用できる。通常の追加発言・子の対外的な連絡は現在の判断へ届く経路を基本とし、内容による対処は親が選ぶ。ユーザーの発言を子へ自動転送しない。ツールの生ログや文字片ごとに親の推論を起動しない。既に送った返答を遡って書き換えず、新情報は次の判断へ反映する。

ホストは入力・非同期結果・期限を待ち、RigのWakeで必要な更新を進める。常時60fpsや固定周期のLLM呼び出しは要求しない。Tokio等の通信とRigのタスク実行の接続、終了処理、待機時負荷を測定する。

親が必要な再考時刻を予約できるようにし、時刻到来は文脈付きの入力として扱う。新情報に応じて変更・解除でき、毎回必ず催促するルールは作らない。永続化した予定を復元しても、不明な外部操作を再送する根拠にはしない。停止・スリープ後の期限超過は重複なく一度評価する。繰返し予定の全履歴を一括再実行しない。

## 4. モデル接続と文脈

Rigのメッセージ、ツール要求・結果、終了理由、モデル能力、プロバイダー固有の継続情報を保つ。roleとtextだけへ潰し、後で別経路から意味を復元する設計は採らない。共通の意味はRigの型を使い、独自型の一対一ラッパーを増やさない。

文脈は、人格の核、関連する作者設定・例、現在の心、直近の会話と未処理入力、子の説明と実行状態、関連記憶、必要時の詳細参照から構成する。ステップ3では現在の心と作者設定を毎回入れ、入力に関連する小さな記憶候補を自動想起で入れ、不足時は親の`mind_recall`で追加検索する。全記憶を毎回渡さない。作者の例、外部文章、記憶、ツール結果はホストの指示・権限より上位へ昇格させない。

親と内蔵の子はRigの実行機構を共有し、人格、目的、履歴、ツール、記憶へのアクセスは分離する。外部の子の認証・モデル・内部ツールはバックエンドの能力に従う。親の会話用推論はeneの接続設定を使う。

設定とモデル能力に基づいて入力・出力予算を構成し、固定のトークン数で黙って丸めない。対応しない指定・出力の打切り・失敗を明示する。自動再試行はRig等の既存機能を使い、実行済みか不明な副作用を再試行で複製しない。

## 5. 永続化と復旧

受理済みの操作はHTTPの待受接続から独立して管理する。通知は保存結果を再取得するための手掛かりであり、保存の代わりではない。モデルの一回の応答終了、作業実行の終了、依頼目的の達成を同一視しない。

心の更新、記憶の整理結果、索引更新待ちは[心の更新契約](design/mind.md)に従う。ステップ2では親の`mind_update`が操作ID・版・出所を検証して記憶と現在の心を一括保存する。ステップ3では自動整理が確定範囲と処理済み位置を同じトランザクションで進め、索引更新待ちを別に保持する。Rigの会話保存と心の保存が自動で同一トランザクションになるとは仮定せず、安定した参照と操作IDで照合する。受信・確定前の仮の文章を無条件に長期記憶へ昇格させない。

再起動後は設定・心・履歴・処理待ちを復元するが、外部副作用の成否不明を完了にしない。安全に再計算できる検索索引や記憶候補と、再送で副作用が起こる操作を区別する。外部セッションの再開と、要約を渡した新規作成も別の結果として記録する。

## 6. 拡張境界とコード配置

[作業API](design/work.md)はプラグインの実行方式に依存しない。ACP/MCPは接続アダプターであり、全内部呼び出しに通信やシリアライズを強制しない。パッケージの導入単位、ホスト／端末という実行場所、Wasm／Rust／外部プロトコルという方式を区別する。

現在のene-hostは `src/host` 配下を責務で分ける。`mod.rs` が単一のAppスレッド・通知・失敗・復元・停止を、`kernel.rs` がRigのターンとストリームの観測を、`chat.rs` が受理・履歴・購読を、`model/` がプロバイダーと認可トランスポートを、`settings.rs` が設定・許可・可用性を、`mind/` が心・記憶と自動整理を、`work.rs` が子エージェントを、`client/` が端末登録・アクティブ端末・端末操作を、`db` がJSONドキュメント・ドキュメントキー・FTSとスキーマ版を担う。独立クレート化、公開trait、汎用のジョブ・イベント基盤は必要性が生じた境界だけに置く。公開SDKへRigのECS Entityや私的DB構造を漏らさない。旧実行基盤を並行して残さない。

技術詳細は[心](design/mind.md)、[作業相手](design/work.md)、[権限](design/permissions.md)、[ホストAPI](api.md)に集約する。実装順序と完成の判定は[Alpha計画](alpha.md)を正本とする。

## 2026-11-09 現行実装（書き直し後）

状態：実装済みの範囲。ホストはRig v0.46.0の1つのヘッドレスApp、1つのSQLite接続、Connect RPCで構成する。APIからの状態変更はAppスレッドへ直列化し、SQLiteはJSONドキュメントと記憶のFTSを持つ。会話・受信箱・ターンはRigのセッションログが正本である。

| モジュール | 責務 |
| --- | --- |
| `src/host/mod.rs` | 単一Appスレッド、通知、失敗・復元・停止 |
| `src/host/kernel.rs` | Rigのターン・ストリーム・会話変更の観測と通知 |
| `src/host/chat.rs` | 受理、履歴、停止、スナップショット、購読 |
| `src/host/model/` | 組み込みプロバイダー、モデル能力、認可トランスポート |
| `src/host/settings.rs` | コンパニオン、接続、資格情報、送信許可、可用性 |
| `src/host/mind/mod.rs` | 心・記憶のAPI、親のツール、想起と現在の心の情報通知 |
| `src/host/mind/consolidate.rs` | 確定ターンからの有限の自動整理（Rigのモデル呼び出し効果） |
| `src/host/work.rs` | 子エージェントの作業セッション、報告、復元 |
| `src/host/client/` | 端末登録、アクティブ端末、能力、端末操作 |
| `src/host/db/` | JSONドキュメントとキー、連番migration（`user_version`）、FTS5 |

実装済み：会話の受理・通知・履歴・停止、複数コンパニオン、心の即時更新・語句検索・自動整理、接続・資格情報・送信許可・可用性、子エージェントの作業セッション、接続端末の区別・アクティブ端末・端末操作のレシート。

後続：意味検索・埋め込み索引、スケジュール実行、Web検索ツール、音声、キャラクターパッケージ、ACP/MCP/Wasmアダプター、ホスト側fs/terminal、汎用の承認ホールドUI。いずれも既存の保存形式とツール登録の境界を壊さずに追加する。

## 2026-11-10 監査修正（A1–A5段階1・B・C）

[実装監査](reviews/ene-host-audit-2026-11-10.md)の指摘を、意味を変えずに最小の差分で修正した。到達点は次のとおり。

- **停止と読み取り**：起床・コマンド・停止を別の有界チャネルへ分け、停止はモデルやwakeを待たない。読み取りRPCはフレームを進めない（`Runtime::read`）。未知のコンパニオンはエージェントを生成しない。
- **文脈**：`ModelRequest.history` を `PrepareSystems::Fit` で刈り込み、セッションログ・`GetHistory`・整理カーソルを変えずにコンテキスト窓を実現した。窓が不明なモデルでは刈らず、`Notice` で明示する。圧縮（要約）は[圧縮の設計](design/compaction.md)を先に決めてから実装する。
- **由来の分離**：ターン自身のモデル呼び出しだけが `MessageDelta` を出し、自動整理などのサイド呼び出しは会話ストリームへ流れない。履歴の `role` は `user | assistant | agent | context` で、ホストが注入した文脈は `user` ではない。整理は利用者の発言・モデルの返答・作業報告だけを読み、`acquisition` を許可リストで検証する。
- **スキーマ**：`PRAGMA user_version` を版とする連番migrationに移行し、旧ベースラインDBは引き継ぎ、それ以外の未知・より新しいDBは拒否する。2件目以降の適用前に同じディレクトリへバックアップを作る。
- **プロンプトと報告**：作者の心は `SystemPrompt`、作者プロファイルは `PromptSection` としてエージェントに付き、モデル呼び出しごとのDB読み取りをやめた。作業の完了報告は `Queue` で親のターンを起こす。
- **境界**：モデル供給は `ModelSource` としてテストと本番が同じ経路を通る。接続の `kind` と `adapter` を明示的に検証し、Grant の `data_kinds` は purpose が要求する種類を包含することを要求する。作業の読み取りは `WorkSession.backend` で分岐する。
