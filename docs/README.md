# ドキュメント

利用・開発環境・起動の手順は[リポジトリのREADME](../README.md)にまとめています。設計や機能の検討は、目的に応じて以下から参照してください。

| 配置 | 内容・配置理由 | 入口 |
| --- | --- | --- |
| `product/` | 何を作るかを定める構想、実装範囲、共通用語。技術的な実現方法と分けて管理する | [構想](product/vision.md)、[MVP](product/mvp.md)、[用語集](product/terms.md) |
| `features/` | 利用者の体験と機能要件。既存の領域別フォルダにまとめる | [機能一覧](features/README.md) |
| `design/` | 実現方法、責務の境界、通信・描画の契約。機能要件から参照する技術設計をまとめる | [アーキテクチャ](design/architecture.md)、[安全性を引き継ぐ共通境界](design/framework-boundaries.md)、[ホストAPI](design/api.md)、[GPU描画](design/avatar-gpu-rendering.md)、[デスクトップUI](design/desktop-ui.md) |
| `research/` | 外部製品・公式資料の調査と採用理由。ene自身の仕様と出典を区別する | [参考元](research/references.md) |

`product/`と`features/`には将来の構想も含まれます。今回の実装範囲はMVP、現在の利用方法はリポジトリのREADMEで確認してください。設計上の方針や検証予定を、実装済み・検証済みの機能として扱いません。

## 追加・更新のルール

- `docs/`直下はこの案内だけにし、新しい文書は上表の目的に合うフォルダへ置きます。既存の話題は対応する文書へ追記し、機能要件と技術設計を重複して記述しません。
- 新しい機能要件は`features/<領域>/`へ置き、[領域用](features/_templates/area.md)・[機能用](features/_templates/feature.md)テンプレートに従います。技術設計は`design/`へ置き、関連する機能要件と相互に参照します。
- 外部資料と採用理由は`research/references.md`に集約し、各文書から該当見出しへリンクします。利用・起動手順はリポジトリのREADME、実装例固有の手順はその例のREADMEを更新します。
- 文書を追加・変更するPRで、配置先と案内リンクも整えます。PRスタックでは、その文書を追加したPRに整理を反映し、後続PRへ引き継ぎます。既存文書の整理は関連するPRでまとめて行います。
- 移動時はリポジトリのREADME、機能文書、テンプレートからの相対リンクと見出しアンカーを更新し、各PRの時点で参照先が存在することを確認します。この案内にも追加・移動を反映します。
- 一時的な検証ログ・スクリーンショット・計測結果はPRの検証記録で扱います。継続して必要な設計判断だけを該当文書に残し、完了した作業報告を仕様と並べて蓄積しません。
