# Alphaホスト：範囲・実装順序・受入条件

状態：採用する設計方針（2026-11-03）。未実装・未測定の段階を含む実装計画であり、全体の動作完了の宣言ではない。ステップ1は実装・モック検証に加え、OpenAIとOpenRouterの実モデルで受入確認まで進んだ。ステップ2（人格と心の即時更新）は基盤を実装し、実モデルで受入確認した。自動記憶・自動想起・意味検索・作業相手は未実装である。旧[MVP](mvp.md)は歴史的資料として残し、本書を現在のホスト開発範囲の正本とする。

## 目的

クライアントの完成を待たず、会話、キャラクターの心、交換可能な作業相手、共有ツールが一連の動作として成立するAlphaを作る。主要な意味と責務を先に固め、細かな操作やUIの追加で中核を作り直さずに済む状態を目指す。将来の変更が一切不要になることは保証しない。

## 実装範囲

| 必須 | 到達点 |
| --- | --- |
| 親と推論 | 最新正式Rigを基盤にした会話・ツール反復、入力の追加、停止、永続化、通知 |
| 人格・心 | 小さな人格の核、関連する側面・例・背景、根拠付きの経験と解釈、現在感情、関係性・成長の保存と利用 |
| 自動記憶 | 即時更新に加えて、保存済みの新しい経験が自動の増分整理へ渡る。語句と意味を使った自動想起と追加検索 |
| 作業相手 | 内蔵の簡単な子と外部接続一系統。継続的な指示・相談・報告、別件の並列実行、個別停止 |
| ツール共有 | 同じ認可付きホストツールを親・内蔵の子・外部の子で利用する |
| 権限と認証 | Rig等の既存機構を優先。新規許可と任された範囲内の判断を区別し、取消と制限の実効範囲を示す |
| API | クライアントから会話・心・作業・設定・相談・停止を扱える。UI内にオーケストレーションを実装しない |

再考予約の最小機構は含める。全文の定期配信サービス、画面見守り、複数端末の実運用、Windows/macOS全対応、本番音声・デスクトップUI、汎用ファイルワーカーの全操作、すべての外部ハーネス対応は後回しにできる。ホストと端末の所在、送信先、操作権限を混ぜるAPIにはしない。

記憶や感情は型だけの仮実装ではなく、実際の会話・作業へ反映させる。巨大な心理シミュレーター、固定の好感度式、毎発言ごとの複数の心理判定モデル、独自の汎用オーケストレーター・OSサンドボックス・ポリシーDSLは初期の必須にしない。

## 実装手順と終了条件

### 1. Rigへの接続

固定版のモデル接続、受信箱、ツール、保存、停止、Wakeを一人の親へ接続する。現行Rig依存からの変更量、Tokioとの接続、待機時CPU、保存失敗・途中停止の扱いを確認する。AvatarのBevy Appとは結合しない。

終了条件：実モデルと一つの無害なツールで会話が通り、追加入力を失わず、停止が推論待ちにならず、待機中にLLMとフレームを回し続けない。同じ状態を二つの実行管理が所有しない。

<a id="alpha-step1-implementation"></a>
#### 実装記録（2026-11-03、PR #10）

- 採用版：Rig v0.46.0（公式リリース 2026-10-31）。`rig-core`・`rig-http`・`rig-ecs`・`rig-memory` を0.46.0で`Cargo.lock`に固定した。調査基準v0.46.0と一致することをリリースとcrates.ioの索引で確認した。
- 実行管理：`rig-ecs`の`AgentPlugin`・`SessionLogPlugin`を専用のヘッドレススレッドで動かし、コンパニオンごとに一つの親エージェントを持たせた。受信箱（`Incoming`/`Deliver`）、ターン、モデル呼び出し、ツール呼び出し、停止（`StopTurn`）、セッションログをRigへ委譲した。AvatarのBevy Appとは別のAppで、描画・フレーム更新を持たない。
- 入力と保存：追加入力は`Steer`で受信箱に入れ、ターンの次のモデル呼び出しへ届ける。会話・受信箱・ターンはRigの`DirStore`セッションログ（`<state>/rig`）へ保存し、履歴取得はそのログを読む。SQLiteから旧メッセージ表への書込みは行わず、旧行は削除しない（会話の移行はしていない）。
- 停止と起床：`Stop`はカーネルへの停止要求を渡した時点で完了し、モデル応答・ツール完了・実行枠の空きを待たない。待機中は起床シグナルと最大1秒の期限だけでフレームを回し、固定周期の推論を行わない。
- モデル接続：認可済みHTTPトランスポート（既存の送信先・資格情報・取消境界）をRigのモデルへ渡す。親の会話は当初、組み込みOpenAI（Responses API）とRigカタログ上のツール対応モデルに限定した（追加受入でOpenRouterを加えた。下記）。Wasmプロバイダーは接続確認・タスク推論で継続利用するが、親会話経路には未接続。資格情報はRigへ渡さず、送信境界で付与する。
- 認可と取消：各送信とストリーム受信で、現在の設定・資格情報・送信許可を再確認する。設定・資格情報・送信許可の変更は、実行中のターンを停止し、次の入力時にモデル連接を作り直す。
- 保存失敗：セッションログの書込み失敗をホストの`HostHealth.recovery_required`へ反映し、新しい会話の受理を止める。停止・失敗・未確認を成功へ変換しない。
- API：`SendMessage`は受理ID（`request_id`）だけを返す。ユーザー発言・返答は`MessageCreated`、実行の開始・終了は`TurnEvent`、文字片は`MessageDelta`（`stream_id`）で通知し、確定内容は`GetHistory`/`GetMessage`で取得する。旧`MessageStarted`/`MessageUpdated`と応答メッセージIDは削除した。
- 検証（モック）：スクリプト化モデルで、ツール1回を含む会話、処理中の追加入力がモデルへ届くこと、ツール実行中の停止が2秒以内に完了すること、待機400msのフレーム数が10未満であること、セッションログ書込み失敗が通知されること、再起動後の会話復元を確認した。ホストAPI統合テストで、受理・通知・履歴・同一要求キーの再送・停止・送信許可取消・再起動を通した。組み込みOpenAI Responsesの本番接続経路は、ローカルのSSEサーバーを相手に、認可済みトランスポート・リクエスト先・資格情報付与・ストリーミング解釈を通した。いずれもスクリプト化した応答で、実際のモデル品質や外部サービスは確認していない。
- 未確認：実モデル・実資格情報での会話（この環境に許可された設定がないため未実施）。会話文脈の自動圧縮・要約、Wasmプロバイダーの親会話経路、旧メッセージの移行は未対応である。

<a id="alpha-step1-live"></a>
#### 追加受入（2026-11-03、実プロバイダー）

上の実装記録の「未確認」のうち、実モデル接続を次の条件で確認した。検証用の一時stateディレクトリ・一時コンパニオンだけを使い、既存データは変更していない。鍵はリポジトリの `.env` から検証プロセスが読み、ホストの通常の資格情報APIへ渡した。値・Authorizationヘッダー・`.env`全体は出力・保存していない。会話は合成の短い文だけである。

- 経路：実ホストプロセス（`ene-host`）を一時`XDG_RUNTIME_DIR`/stateで起動し、認証付きConnect RPCで接続・資格情報・Grant・モデル割当を設定した。`SendMessage`で受理し、Rigカーネルが実プロバイダーを呼び、`current_time`ツールを実行し、結果をモデルへ戻し、最終応答を保存した。Rigのセッションログでツール要求（`"current_time"`）とツール結果（`"type":"toolresult"`と時刻）を直接観測し、文章だけでは判定していない。
- OpenAI：モデル`gpt-6-luna`（Rigカタログのツール対応・低コストモデル。既存の組み込み指定）。2ターン（初回はツール往復を含む2回のモデル呼び出し、追撃1回）。取得できたusageは入力473・出力69トークン、Rigカタログ単価からの参考コスト0.0000818 USD。追加試行を含む呼び出し回数は別記する。
- OpenRouter：組み込みのOpenRouter接続（OpenAI互換Chat Completions）を追加し、OpenRouter自身の`/api/v1/models`・資格情報・送信先許可で`google/gemini-2.5-flash-lite`を呼んだ。2ターン・3回のモデル呼び出し。取得できたusageは入力444・出力70トークン、参考コスト0.0000724 USD。OpenAIの接続設定は流用していない。
- 共通の確認：`MessageCreated`・`MessageDelta`・`TurnEvent`の対応、確定テキストがツール結果の時刻と一致すること、次の発言で前の会話が引き継がれること、SIGTERM→再起動後に`GetHistory`で4メッセージが復元されること。
- 未取得：上記2回の成功シナリオ以外の試行のusageは一時領域の削除で失われ、記録していない。料金はプロバイダーの請求額ではなく、Rigがカタログ単価から計算した参考値である。

#### OpenRouterとプロバイダー拡張

- OpenRouterはRigのネイティブ接続（`OpenAIConfig::with_key(&OPENROUTER, ...)`とChat Completions）を親の会話に追加した。ホストのOpenRouter記述子・資格情報・送信先許可・モデル一覧（`/models`）を持つ。Rigカタログにあるモデルはその能力を使う。
- カタログにないモデルの制限は「未知＝非対応」とせず、接続の`options`の`{"tool_calling": true}`を明示した場合だけ、その宣言を根拠にツール対応として扱う。`false`は`model_cannot_call_tools`、指定なしは`model_capability_unknown`として区別する。未知のモデルを推測で対応済みにはしない。
- 現行Wasmプロバイダーは一つの推論のストリーム変換であり、ハーネスのツールループではない。ワイヤには`GenerationRequest.tools`と`Event::ToolCall`があるが、ホスト側アダプターは`tools: Vec::new()`を固定し、`ToolCall`を未対応として拒否し、ホストの`Generation`/`ChatMessage`はroleとtextしか運べない。ツール対応WasmプロバイダーをRigへ接続するには、ツール定義・ツール呼び出し・ツール結果を往復するホスト側契約と、Rigの`Serve`ハンドラーへの薄い変換が必要である。別のエージェントループは不要で、Rigがターンとツール実行を保持できる。前回の「別ループの複製が必須」という記述は、契約の不足とループの複製を混同していたため訂正する。
- OpenRouterの接続確認（`CheckConnection`）とタスク推論の単発生成は未接続で、呼ぶと明示的に非対応を返す。親の会話受入の判定とは別である。

#### 追加の不変条件（2026-11-03）

- 出力上限：ストリーミング文字数の上限に加え、RigのReview段階で確定前の返答文字数を検査する。単一の巨大イベントで上限を超えた返答は保存・通知せず、ターンを`output_limit`の失敗にし、入力を`RecalledInput`でクライアントへ返す。回帰テストで、返答メッセージが通知されず、履歴に残らず、入力が返ることを確認した。HTTP本文の8MiB上限は別の防御である。
- 受付と保存：`SendMessage`の受理は、Rigが入力を開始し、そのフレームのセッションログ書込みが成功した後に返す。セッションログが書けない場合は受理せず、エラーにする。再起動後に残った未確定の会話レシートは、同じ`request_key`の再送時にRigの保存済み会話・受信箱を`request_id`で照合し、見つかれば元の受理を返して再配送せず、見つからなければ503で確定する。この経路と二重配送がないことを統合テストで確認した。別の`request_key`で送り直した場合の重複は、元の受付応答を受け取れなかった場合に区別できないため残る。
- 待機時CPU：NixOS / x86_64、リリースでない標準テストビルドで、初期化1秒後から10秒間を観測した。CPU時間0.020秒（0.20%）、フレーム10回（1回/秒）、Rigの起床0回。1秒周期の期限起床は、遅延した再試行・期限確認のためのもので、完全休眠だけを目的に新しいスケジューラーは作らない。
- 旧SQLiteメッセージ：旧`messages`表は削除せず、読み書きもしない。移行機構は作らない。旧データが現在の会話に含まれないことをREADMEと本節に明記する。

#### ステップ1の判定

OpenAIの実ホスト経路とOpenRouterのネイティブ接続で、実モデル・無害なツール1つ・ストリーミング・確定履歴・追撃・再起動を確認した。ステップ1の必須条件「少なくとも一系統の実モデルと無害なツールを通す」は満たした。追加入力・停止・取消のタイミング依存の性質は決定論的モックで確認しており、実モデルで同じタイミングを再現したとは扱わない。未対応はWasmプロバイダーの親会話接続、OpenRouterの接続確認・タスク推論、文脈圧縮、実クライアントUIである。ステップ2（人格と心の即時更新）へ着手できる状態だが、本変更では開始しない。

<a id="alpha-step2-implementation"></a>
#### ステップ2の実装記録（2026-11-03、PR #10）

著者設定と実体験・現在の心を分離し、親の通常のRig推論から心を更新・参照できる最小経路を実装した。会話の実行管理・ターン・ツール実行は引き続きRigが持ち、第二のエージェント実行基盤は追加していない。心と記憶の正本はSQLite、会話の正本はRigのセッションログである。

- 人格の核は既存の`Companion.mind`、側面・会話例・背景・表現語彙は`mind_companions.profile`に保存する。会話例は「実体験として記憶しない」とプロンプトで明示し、記憶テーブルへは自動的に入らない。著者プロファイルと権限は、モデル用の更新要求型からフィールドとして存在せず、`serde`の未知フィールド拒否で拒否される。
- 記憶は`mind_memories`、現在の心は`mind_companions.state`、操作の適用結果は`mind_operations`に保存する。`SourceRef`（受理入力・記憶・操作）、`MemoryRecord`（内容・評価・取得方法・出所・記録時刻・発生時刻・関連・訂正・想起優先度）、`MindState`（感情・関係・傾向・気にかけていること）、`MindChange`（操作ID・更新元・revision・記憶追加・訂正・心の変更）の意味を保持する。型ごとの独立テーブルや汎用traitは作っていない。
- `mind_update`は、所有者・操作ID・入力出所・更新元（親）をホストの実行文脈から束縛する。1回のSQLiteトランザクションで記憶・現在の心・操作記録を確定し、同じ操作ID・同じ内容の再試行は元の結果、同じID・異なる内容は競合、古いrevisionは競合として、部分変更を残さない。操作記録には更新元と出所も保存し、ツール結果の記録が失われた後に同じ内容・同じ入力出所で再送された場合は、新しい操作IDでも適用済みの結果を返して二重適用しない。変更なしも成功結果として記録する。参照する記憶IDは同一コンパニオンの所有物かを検証する。
- 親には`mind_recall`（検索）、`mind_read`（詳細・出所・訂正関係）、`mind_update`（構造化更新）をRigのツールとして接続した。mindツールを持つのは最初の（Alphaでは唯一の）親コンパニオンだけで、他の親・子・外部MCPには公開しない。現在の心の概要はsystem promptへ毎回入れ、呼び出しのたびに状態取得を強制しない。
- `mind_update`のコミット後、同じターンの次のモデル呼び出しへ現在の心とrevisionを反映する。モデルの再接続・ターン停止は行わない。接続時はSQLiteからプロンプトを再構成するため、会話用モデルの変更・再起動でも心は初期化されない。
- 検索は、クエリ全体と日本語文字bigramをSQLiteの`LIKE`で照合する最小の語句検索である。固定結果や全件返却ではない。FTS5・意味検索・自動想起・自動整理はステップ3に残した。
- ホストAPIに`GetMind`（著者プロファイルの核と追加材料、現在の心、profile/stateのrevision）と`UpdateMindProfile`（追加材料の著者編集。既存の`UpdateCompanion.mind`が核）を追加し、保存成功後に`MindUpdated`を通知する。`mind_update`の保存成功時にも通知する。記憶一覧のクライアントUIは未実装である。
- 機械検証：`ene-host`のlibテスト130件（ほかに実ホストプロセスの統合テスト）。同じ操作の再試行・同じ内容と入力出所の再送（新しい操作ID）で二重適用しないこと、異なる内容の同一操作ID・古いrevision・他コンパニオンの記憶参照・不正なフィールドを拒否すること、記憶挿入失敗時に状態・revision・操作記録をロールバックすること、訂正が旧記憶を残して`supersedes`/`superseded_by`を持つこと、所有者を越えた検索をしないこと、変更なしが成功すること、保存とプロファイル通知、再起動後の保持、スクリプト化親の`mind_update`が同じターンの次のモデル要求へ反映されることを確認した。実モデルのタイミング依存（追加入力・停止）は引き続きモック確認である。
- 実モデル受入（一時state・合成会話）：OpenAI `gpt-6-luna`で、初回更新（revision 2、2モデル呼び出し、入力2335・出力163トークン、参考コスト0.00037323 USD）、訂正（revision 3、4呼び出し、入力7325・出力266、0.00054566 USD）、会話を持たない再起動先での`mind_recall`（2呼び出し、入力2671・出力51、0.00023457 USD）を通した。再起動先の応答は保存記憶だけから「現在はりんご、以前は柚子」と区別し、元会話文は新しいRigログになく、現在の心のプロンプトにも果物名を含めなかった。最後に会話モデルをOpenRouter `google/gemini-2.5-flash-lite`へ変更し、同じ記憶を`mind_recall`で読めること（2呼び出し、入力3240・出力33、0.00026043 USD）を確認した。合計10モデル呼び出し、入力15571・出力513トークン、参考コスト0.00141388 USD。料金はRigのカタログ単価からの参考値で、請求額ではない。usageは最終受入実行のRigセッションログから取得し、試行錯誤分は含めない。
- 未対応・ステップ3へ残すもの：自動整理ジョブ・自動想起・FTS5/意味検索・忘却・共有プール・古い整理の競合解決。今回はそれらの常設エージェント、汎用ジョブ基盤、空のモジュールを作っていない。ただし記憶の出所・操作ID・revision・更新元・取得方法・訂正関係は保存しており、後続の整理処理が同じ`mind_update`検証・トランザクションを再利用できる。

#### ステップ2の判定

終了条件「会話から記憶と現在感情を更新し、次の判断と表示用状態へ反映する。再起動しても保持でき、架空の会話例が実体験へ混入しない」は、機械検証と実モデル受入の範囲で満たした。ただし自動記憶・自動整理・長期的人格品質は未完成であり、ステップ3の完了を意味しない。

### 2. 人格と心の即時更新

作者設定と実体験を分け、現在の心を文脈へ投入する。mind.recall/read/updateの最小経路、SQLiteの原子的更新、操作IDによる重複防止、根拠の参照を実装する。

終了条件：会話から記憶と現在感情を更新し、次の判断と表示用状態へ反映する。再起動しても保持でき、架空の会話例が実体験へ混入しない。

### 3. 自動記憶と検索

未処理範囲からの有限の整理ジョブ、自動想起、全文・意味検索、索引更新待ちを追加する。訂正、忘却、共有、版の変更を正本で検証する。記憶の形成が親の任意の保存操作だけに依存しないことを確認する。

終了条件：明示的な記憶依頼なしに関連情報が形成される。遅い整理が現在感情を巻き戻さず、再試行で重複せず、古い索引から非公開情報が漏れない。元情報の圧縮と整理待ちの関係を確認する。

### 4. 子と共通ツール

親と実行機構を共有する内蔵の子をWorkSessionとして接続する。親の会話とは別の履歴と権限で動かし、受付後の進捗・相談・終了を通知する。別件を同じ設定から並列に始める。

終了条件：作業中の会話、普通の追加指示、子の相談への回答、結果を受けた追加修正、片方だけの停止が成立する。ツールの実装と認可を複製しない。

### 5. 外部アダプターと制限

実際のACP接続一系統とMCPツール公開を接続する。公式SDKを使い、能力・認証・モデル設定・継続・停止を確認する。逆方向の最小ACP公開と、小さな独自プラグインでも意味の対応を検証する。

終了条件：eneの論理APIがACPの全機能を強制せず、対応する部分は薄い変換で利用できる。未対応・未配送・実行中・失敗を成功へ補完しない。信頼して導入する外部実装の制限範囲を記録する。

### 6. 長期評価と削減

別検索構成と別バックエンドを小さく試し、親と心を変えずに交換できる境界を確認する。必要性が未確認の抽象化、旧契約、独自の標準プロトコル処理を除去する。二実装の本番同梱を完成条件にはしない。

終了条件：下記の機械的な不変条件と体験評価を分けて記録し、性能・品質・未対応範囲を明示する。

## 検証

機械的テストは、重複実行、情報の混線、権限、状態破壊、失敗の成功扱いへ集中する。依存ライブラリの全仕様や定数の写し合わせを再テストしない。

| 不変条件 | 代表的な確認 |
| --- | --- |
| 更新は一度 | 同じmind.update、整理範囲、索引更新の再試行で二重の経験・感情変化を生まない |
| 由来と隔離 | 作者例・共有情報・子の報告・直接観測を区別し、他者の私的記憶を引かない |
| 遅い結果の扱い | 古い整理が新しい心を上書きせず、忘却・訂正を巻き戻さない |
| 状態の正確さ | RPCエラー、出力打切り、キャンセル、配送不明を完了・目的達成へ変換しない |
| 停止と復旧 | 操作受付と完了を分け、再接続や再起動で不明な副作用を再送しない |
| 取消 | ホストの新しい操作・送信に取消を適用し、外部側の残る制約を隠さない |

体験評価では同じモデル・予算・履歴で、人格と履歴のみ、人格の側面と例、即時記憶、自動整理と持続する心を段階的に比較する。初対面、好みの自然な学習、協働の失敗と成功、後日の想起、訂正、一部共有、実務の再依頼を通す。固定台詞の一致ではなく、根拠の連続性と人格・関係・感情・記憶を別に評価する。[研究根拠](references.md#alpha-evaluation)

形成・検索・利用を混同しない。保存されなかった記憶、検索で落ちた記憶、渡したのに誤用した記憶を区別する。匿名の独自キャラクターも使い、モデルが有名キャラクターの名前から知識を補う効果を分離する。

性能は、追加推論数・トークン、初回応答と停止の遅延、待機時CPU、検索・索引構築中のメモリ、保存量を測る。数値目標は実測前に作らず、評価記録に環境・モデル・版を添える。品質の改善なく処理が増える要素は採用しない。
