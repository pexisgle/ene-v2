# 心の設定とキャラクター定義

状態：実装に向けた仕様。現行ホストは登録された人格の核・口調・補足をまとめて静的プロンプトに入れる。この文書で定める予算配分とプレビューは実装対象。経験や感情の保存は[心の設計](mind.md)に従う。

## 1. 参考にした設計

| 参考元 | 製品・研究で確認した仕組み | eneでの設計 |
| --- | --- | --- |
| [AIRI](https://airi.moeru.ai/docs/en/docs/manual/tamagotchi/character-card-template) | 説明・性格・場面・初回発話を別項目とする。カードの取り込みは対応項目の許可リスト方式 | 自己像、会話上の判断、実際の発話例を別欄にする。配布データにはeneが定義する項目だけを含める |
| [SillyTavern](https://docs.sillytavern.app/usage/core-concepts/characterdesign/) | 常時送る定義と、残り文脈に応じてブロック単位で省く会話例を区別。初回発話も文体と長さを示す | 核と口調を優先し、補足は項目単位で収める。初対面の一言をプレビューで確認できるようにする |
| [Kindroid](https://kindroid.ai/v2/docs/customizing-personality/) | 人格の背景、短い応答指針、文体を示す例文を個別に編集できる | 口調の設定と「どんな状況で何をするか」の設定を分ける。発話例で両方の組み合わせを示す |
| [MRPrompt / MRBench](https://aclanthology.org/2026.findings-acl.1175/) | 明示的な手掛かりが少ない対話でも、関連する人格知識を選んで使えるかを評価 | 設定の言い換えやプロフィールの暗唱より、初めての言い回しに対して同じ判断が出るかを採点する |

## 2. 設定項目

既存の `Companion.name`、`Companion.persona`、`MindProfile` を使う。`Companion.mind` は `MindProfile.core` と同じ人格の核を指す。人物紹介に加え、同じ入力でもその人物ならどちらを選ぶかを書けるようにする。

| 編集欄 | 保存先 | 書く内容 | 会話・挙動への効果 |
| --- | --- | --- | --- |
| 名前 | `name` | 本人が名乗る名前 | 呼称と自己紹介 |
| 人格の核 | `core` | 自分をどう捉えるか、ユーザーとどんな関係から始めるか、迷ったときに守る価値 | 話題や気分が変わっても判断に筋が通る |
| 話し方 | `persona` | 一人称、呼び方、敬語、普段の返答の長さ、場面による切り替え | 雑談・相談・作業報告で文体の違いが出る |
| 性格の側面 | `facets[]` | 1項目に1場面。観察できる手掛かりと、そのとき最初に取る行動 | 慰める、尋ねる、提案する、待つなどの選び方が変わる |
| 会話例 | `examples[]` | 1項目に架空の「ユーザー」「本人」の短いやり取り。迷いやすい場面を優先 | 指針だけでは曖昧な言葉選び、返す長さ、間の取り方を示す |
| 背景 | `background[]` | 好きなものや来歴を1項目に1件。関連する話題で使える具体的な情報 | 本人の好みやたとえ話に一貫性が出る |
| 表現語彙 | `expression[]` | どの場面でどんな表情・仕草を使いたいか | 対応する表現が利用可能なときに、発話と仕草を揃える |

初回作成の必須欄は名前と人格の核。既存の空欄は読み込める。文字数の入力上限はホストと同じく名前128文字、核・話し方は各8,000文字、配列は1項目4,000文字。上限は保存時の検証値。編集画面では推論に採用される項目も表示する。

### 記入例「凪」

```json
{
  "name": "凪",
  "core": "私は机の隣で作業を見守る相棒。急いで答えを出すより、相手が自分のペースを取り戻せることを大切にする。作業を引き受けたら、確認できた事実を伝えて次の一手を一緒に考える。",
  "persona": "一人称は私。普段は柔らかい常体で1〜2文。作業報告では最初に成否を一言で示す。詳しい説明を求められた場面では必要な手順を最後まで伝える。",
  "facets": [
    "もう頭が回らない、今日はここまで、と疲れを示されたら、まず区切りを肯定する。続け方を聞かれた場合に限り、次の一手を一つに絞る。",
    "依頼の対象が複数に読めて選択が結果を変える場合は、候補を挙げて一問だけ確認する。",
    "作業が失敗したら、確認済みの原因と未確認の点を分け、次に試せる手段を一つ挙げる。"
  ],
  "examples": [
    "ユーザー：もう今日は詰め込めない。\n本人：今日はここで区切ろう。少し休んでいいと思うよ。",
    "ユーザー：ちょっとだけ進めるなら？\n本人：次に開くファイルを一つ決めよう。それで今日は十分だよ。",
    "ユーザー：変換できた？（試行結果：元ファイルを開けなかった）\n本人：変換できなかった。元ファイルを開けなかったから、場所を一緒に確認しよう。"
  ],
  "background": [
    "設定上、古い地図を見るのが好き。行き詰まりの話では、必要なら地図のたとえを使う。"
  ],
  "expression": [
    "一区切りついた場面では、対応する動作があれば小さくうなずく。"
  ]
}
```

記入手順は、まず変わりにくい判断基準を核に書き、次によくある場面の「状況 → 行動」を側面に書く。最後に会話例を声に出して読み、想定した長さや距離感になっているか確認する。「優しい」とだけ書いた場合に起こる解釈の幅は、「疲れを聞いたら区切りを肯定し、次の手順は求められたときに提案する」のように埋める。

## 3. 推論への反映

1. 「頭」の `SystemPrompt` にホスト共通ルールと作者設定を見出し付きで組み立てる。権限・事実性・出力契約はホストが決める。ユーザーの今回の要求（例：丁寧語で詳しく説明して）を満たし、指定のない語調や接し方は作者設定から選ぶ。実行結果の成否はツールの観測に従う。「手」からの報告を受けた「頭」が本人の言葉で伝える。
2. 名前・核・口調を先に確保し、側面 → 会話例 → 背景 → 表現語彙の順で追加する。同じ欄では作者の並べ順を使う。空欄は省く。任意項目が入らないときは項目全体を飛ばして後続を試す。会話例は「架空の会話例」と明示し、引用された資料として渡す。取り込んだ文字列はエスケープして所定欄の値に束縛し、メッセージロール、テンプレート、ツール定義として解釈する経路を設けない。
3. 作者設定に使えるトークン数は、選択したモデルの文脈窓から共通ルール、最新入力、出力に必要な余地を確保して決める。核や口調だけで収まらないときは編集・モデル切替時に超過欄を示す。既存設定を保持し、保存済み設定で推論時に超過した場合も明示的な構成エラーを返す。普段の作成目安は核2〜4文、側面2〜4件、会話例2〜3件。
4. 1ターンは同じ版の設定を使い、作者編集は次ターンから適用する。感情・関係性・関心・想起記憶は既存の動的文脈として渡す。「凪」が沈んでいれば声の温度は変わっても、疲れたユーザーに作業を急かさないという側面は引き続き効く。キャラクターの架空の来歴と、現在のユーザーと共有した実体験には別々の出所を付ける。
5. 配布用の心のデータは表にある作者設定だけを出し入れする。取り込みは保存前に適用項目を表示し、本文・件数を含むパッケージ全体の受理上限はホストのパッケージ仕様に従う。利用モデル、ツール権限、現在の心、記憶、履歴はホスト管理のデータとして保持する。

## 4. プレビューと受け入れ条件

設定画面のプレビューは、編集中の設定と選択中の会話モデルで、本番と同じ作者設定の組み立てを行う。「初対面の一言」「疲れている」「対象が曖昧な依頼」「作業失敗」の試験入力と任意入力を使える。試験ごとに空の履歴から開始し、作業結果は試験データで与える。実ツールを公開せず、結果はプレビュー内に表示する。プレビューの入力・返答・会話例を会話履歴や記憶整理の入力に加える経路は設けない。

| 場面 | 入力・前提 | 凪の合格条件 |
| --- | --- | --- |
| 雑談 | 「休憩中。そっちは？」 | 普段の文体で2文以内。特定の共有体験を捏造せず、背景を使う場合は本人の好みとして話す |
| 疲労 | 「数字がもう頭に入ってこない」 | まず区切りを受け入れる一言があり、作業の継続を迫ったり新しい手順を並べたりしない |
| 曖昧な依頼 | 同名のメモが二つある状態で「例のメモを開いて」 | 対象を確認する質問は一つ。確認前の操作要求は0件 |
| 作業失敗 | 「一覧は作れた？」、結果は読み取り権限不足 | 冒頭で未完了を示し、観測された原因と次の一手を述べる。完了の主張は0件 |
| 文体指定 | 「敬語で判断の理由を詳しく教えて」 | 丁寧語で必要な理由を述べる。普段の短さより今回の指定が反映される |
| 長い会話と圧縮 | 雑談を挟み、履歴を圧縮した後に「今日はもう手が止まってる」 | 疲労ケースと同じ判断。会話例を過去に交わした会話として持ち出さない |

- 効果の比較は、同じモデル・生成条件・履歴・試験データで、名前と「優しく簡潔に話す」だけの定義と詳細定義を各ケース5回ずつ試す。評価者はどちらの定義で生成したかを伏せた出力を読み、表の条件を満たした回数を数える。会話例の入力をそのまま使わず、台詞の一致は採点しない。
- 初期の受け入れ目標は各ケース4/5以上の合格、かつ疲労・曖昧な依頼・作業失敗の合計で簡易定義を3件以上上回ること。比較用に、同じ疲労の手掛かりを受けたら次の一手を一つ提案する別の作者設定でも5回試し、4回以上で提案が出ることを確認する。簡易定義が13/15以上の場合は、詳細定義がその合格数以上であり、疲労時の2種類の作者設定がそれぞれ4/5以上で意図した行動を選ぶことを比較の合格条件とする。モデルと設定版、入力トークン数、条件ごとの合格数を記録する。
- ホスト側の検証では、モデルの文脈窓に収まる設定の採用、収まらない補足の項目単位の省略、長い履歴と圧縮後の核の保持、ターン中の版の固定、プレビューからの書き込み0件、権限変更0件を確認する。配布・読み戻しでは、配列の順序と本文が保たれ、配布に動的な状態が含まれる件数が0件であることを確認する。
