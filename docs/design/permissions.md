# 権限・承認・実行制限

状態：Alphaの採用設計（2026-11-03）。製品としての振る舞いは[権限とデータの管理](../features/settings/permissions.md)を維持し、ここでは既存機構への接続と保証範囲を定める。コード・OS隔離の実装完了を意味しない。

## 1. 三つの責務

| 責務 | 担当 |
| --- | --- |
| 意味の判断 | 親が、依頼と文脈から必要な操作・既に任された範囲・相談の要否を判断する |
| 承認の実行管理 | RigのGate、Decision、Hold、Ask等を使い、操作の前で保留・回答・拒否を扱う |
| 実効的な制限 | ツール、認証付き接続、既存OSサンドボックス、外部ハーネスが適用する |

LLMによる自然な判断だけをアクセス境界にしない。感情・親愛度・過去の好みは権限を増やさない。操作名だけで一律に確認せず、ユーザーに複雑な承認ルールの編集を求めない。

## 2. 再利用するもの

Rigの実行前判定、保留、質問、回答、操作結果と記録を優先利用する。ApprovalPluginは複数の理由をまとめる機構として評価するが、確認した実装は回答者がいなければ拒否する。eneの離席時の保留へそのまま適合すると扱わない。既存のHold・Askに親とクライアントの回答経路を接続し、操作全体と関係のない承認フラグや独自の二重キューを作らない。[根拠](../references.md#alpha-permissions)

Rigのsandbox corpusは拡張例であって、完成した汎用権限サービスではない。プロセス起動の共通境界を利用し、OS隔離は既存の実装へ委譲する。Anthropic Sandbox Runtime等は配布依存・版・対応OS・既定値・取消の制約を検証して選ぶ。ライブラリ機能の存在だけを安全性の証明にしない。

独自のAI審査エンジン、汎用ポリシーDSL、OSサンドボックスの複製は初期の必須にしない。Cedar等は現行の要件を単純な許可データで表せない必要が実証された場合の候補にとどめる。

## 3. eneが保持する許可の意味

許可は、主体、対象の所在環境、機能／操作範囲、資源または接続先、必要ならデータ種別と用途、状態と版を持つ。ホスト接続許可、端末の操作許可、外部サービスへの送信許可、プラグインを信用して起動する判断を同一視しない。

許可の範囲はツールの引数や接続設定からホストが構成する。モデルにホスト所有者の主体や全権トークン、任意のgrant idを選ばせない。MCPのreadOnly等の自己申告は補助情報であり、未信頼のツールの認可の根拠にはしない。

現在の許可・資源・接続先を変更しない操作は、その都度の確認を要求しない。コードの更新だけで常に再承認が必要という方針にも、信用済みなら無条件で許可を継承する方針にも固定しない。パッケージの同一性・実装変更の検知と、権限範囲の変更を分け、必要な差分を示す。

## 4. 自然な相談と権限付与

親は既に任された操作を選べる。新たな資源・送信先などの許可は、ユーザーの意思と認証された操作に結び付ける。親が自分を人間の回答者として登録して、許可を自作する経路は作らない。

承認要求には対象操作、資源・送信先・影響、必要な範囲、作成時点の版、request idを紐付ける。ユーザーの事前の指示に合意が含まれる場合は、同じ相談を繰り返さず既存の委任へ対応付けられる。モデルが文脈の解釈を助けても、提案した操作と許可する操作が同一であることはホストが検証する。

質問は親が会話に整理するが、回答の対応先は不透明なrequest idで追跡する。別の操作への承認を次のコマンド用の一ビットへ変換しない。allow_onceと継続許可の範囲も同一視しない。

ユーザー不在なら判断が必要な操作をHoldして保存し、無関係な作業まで停止しない。クライアントの接続有無だけで自動許可・自動拒否にしない。再接続時に未決事項を取得し、同じ要求を重複通知しない。再起動後に副作用の継続が不確実なら、古い保留を勝手に再実行せず現状を照合する。

## 5. 実行と取消

認可は受付だけでなく実行開始・送信の境界でも確認する。要求待ちや質問の間に権限が変わった場合、古い承認を流用しない。停止・取消が通常の実行枠の空きやLLM応答を待たない経路を維持する。

ホストが管理する権限を縮小したら、新しい関連操作・送信を止める。既に開始した処理は実際に可能な方法で取消・終了確認し、送信済みデータや完了済みファイル変更を巻き戻したとは報告しない。

OS隔離の規則が実行中に変更できない場合は、対象プロセスを停止して制限付きで再起動するか、その機能を利用不可とする。設定値だけ変更して取消が効いたことにしない。停止要求の受付と、停止完了・不明・失敗を区別する。

## 6. 外部ハーネスとサンドボックス

インストールして信頼した外部ハーネスは、自身の認証とツールを持てる。eneのMCPツールはeneの認可で制限し、外部ハーネスの自前ツールはその実行基盤へ委譲する。ACP自体をOS隔離とは呼ばず、terminal capabilityやcwdの指定を、プロセス全体のシェル・ファイル・通信禁止として扱わない。

terminal capabilityが受け取るenvironmentは、bindingが列挙した変数名だけを通し、列挙がなければ要求のenvを一切適用しない。許可したコマンド名は実行ファイルの種類しか制限せず、引数・環境・子孫プロセスの隔離を意味しない。

| 実行区分 | 表示と保証 |
| --- | --- |
| ホスト管理ツール | eneが適用する資源・送信先・操作制限を表示する |
| 制限付きの外部実装 | 実際に適用したハーネス／OS制限、対応する停止・取消を表示する |
| 信頼して起動するネイティブ実装 | OSユーザー権限等の実効範囲を明示し、狭い許可フォルダに隔離済みと表示しない |

任意の狭いアクセス保証を満たせない操作を、その保証付きで有効化しない。外部実装が広い権限を必要とする場合は、利用者が実効範囲を理解して選ぶ接続として区別する。範囲が不明なものを安全側と推測しない。

サンドボックス採用時は読取・書込・ネットワーク・IPC・プロセスツリー・資格情報・実行中取消を別々に確認する。既定の読取が広い製品を許可フォルダ専用と呼ばない。ネットワーク遮断と送信先フィルタリングも別である。

## 7. 秘密情報とデータ送信

秘密情報はOSの資格情報ストア等で管理し、通常の会話・記憶・研究ログへ保存しない。取得APIや子への共有で所有者トークンを公開しない。認証方法は静的キーに固定せず、必要なログイン・更新・失効はRigや既存アダプターへ委譲する。

会話、記憶整理、埋め込み、外部検索、再ランキング、子への委譲は、送る情報と宛先をそれぞれ識別する。同じ会話モデルを許可したことが、別の記憶サービスへの送信許可にはならない。許可範囲でまとめて利用できるようにし、呼び出しごとの無意味なダイアログは増やさない。

クライアント認証、記憶の共有、モデルへの送信、ツール実行を同じオン・オフにまとめない。信頼されたプラグインであっても、eneが仲介する秘密情報とツールの能力は明示的な範囲へ束縛する。

## 8. 検証条件

許可済み範囲の通常操作に重複確認がないこと、新規範囲を親だけで付与できないこと、保留中の設定変更を再検証すること、離席中の相談が復元できることを確認する。外部の実効権限、制限の失敗、取消できない部分を表示で隠さない。

採用するOS隔離や認証連携の実機検証結果は[Alpha計画](../alpha.md)へ記録する。設計文書の追加だけで、その隔離が実装・検証済みになったとは扱わない。
