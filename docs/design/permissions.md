## 1. 目的と多層防御アーキテクチャ

システム全体の安全性と自律性を両立するため、3層のセキュリティ境界を定義する。
ユーザーに複雑なアクセス制御リスト（ACL）を設定させることなく、直感的かつ確実にPC環境を保護する。

```text
 ┌────────────────────────────────────────────────────────┐
 │ 外部・作業タスク実行（Hands / WorkSession）             │
 └───────────────────────────┬────────────────────────────┘
                             │
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第1層】機械的な許可（Deterministic Rules）           │
 │  ・ホスト管理の安全ツール、保存済み「常に承認」ルール  │
 └───────────────────────────┬────────────────────────────┘
                             │ (未登録操作)
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第2層】Decision API（安全確認 ＋ 自由文ポリシー判定）│
 │  ・操作の安全性と、自由文ポリシー基準への適合を評価    │
 └───────────────────────────┬────────────────────────────┘
                             │ (危険・ポリシー抵触・失敗時)
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第3層】ユーザー承認（最小限の最終確認）              │
 │  ・画面承認カード、または「頭」が会話文脈から代理承認  │
 └────────────────────────────────────────────────────────┘
```

## 2. 第1層：OSネイティブSandboxと非対応環境の扱い

### 2.1 Sandboxの位置づけ（非必須）
- OSネイティブのSandbox隔離は要件にしない。ホストは`bwrap`や`cap-std`による隔離境界を持たず、`process-wrap`は子プロセスの起動・終了とプロセスグループの管理だけを行う。
- Sandbox非対応環境に対する警告カードや確認ダイアログは出さない。安全性は第2層の判定パイプラインと第3層の承認で担保する。

---
## 3. 第2層：判定パイプライン（Decision Pipeline）

エージェントが提案した操作（Candidate Action）について、以下の厳格な優先順位で機械的・決定論的に検証を行い、必要な場合のみLLM補助判定へ回す。

$$\text{ハード禁止} \longrightarrow \text{明示的毎回確認} \longrightarrow \text{機械的保存ルール照合} \longrightarrow \text{LLM補助判定} \longrightarrow \text{ユーザー承認・親エージェント相談} \longrightarrow \text{実行直前検証}$$

1. **ハード禁止（Hard Deny）**: システムファイル破壊、認証情報・秘密鍵ファイルへの読み書き（`.ssh` / `.aws` / `.env` / システム資格情報ストア等）、危険コマンドパターンなど、保存ルールやLLM判定より優先して無条件で拒否する操作。
2. **明示的毎回確認（Every-time Confirm）**: 外部送信や機密操作など、設定で「毎回確認（`confirm`）」と指定されたカテゴリ。保存ルールが存在しても優先して人間の確認へ回し、LLM補助判定（`ask_llm`）とは区別する。
3. **機械的保存ルール照合（Saved Rules）**:
   - `(tool_name, target)` の厳密な対象照合で判定する（任意の文字列引数への広すぎる一致は行わず、パス・URL・ホスト・コマンド等の正規化済み操作対象のみを照合する）。
4. **LLM補助判定（Decision Engine）**: `ask_llm` ルールまたは未登録操作の文脈適合性を評価。外部送信を伴う組み込みツール（`web_search`）、MCPツール、Wasmプラグインツールもすべて同じ `Stage::Gate` パイプラインを通る。
5. **対話的確認（Human-in-the-Loop）**: 親エージェントがユーザーの意図を汲み取って対話的に確認・仲介。
6. **クライアント操作の対象検証**: `device_request`では、受付時に束縛した`client_id`、能力の`input_schema`、承認ハッシュ`action_payload_hash`を検証する。配送先は常にその`client_id`であり、アクティブクライアントが別端末へ切り替わっても承認を失効させず、保留中の呼び出しを新しいアクティブクライアントへ付け替える。

端末の能力を付与するルールは `client_capability` を対象にする。操作の確認を省略するルールは、端末が宣言した新しい能力を付与しない。作業フォルダーの能力は、その能力にツール名が宣言されていても手から呼び出す。

### 3.1 入力遮断型AI判定（Decision Engine）の多層防御
- **インジェクションに対する現実的認識**:
  - Candidate Actionには、外部Webページや取得ファイルから誘導された引数（URL、コマンドパラメータ、送信メール本文等）が含まれ得るため、「プロンプトインジェクション完全防御」は成立しない。
  - したがって、AI判定は境界そのものではなく、多層防御の1要素として位置づける。
- **入力要素の限定**:
  1. `Candidate Action`: ツール名、正規化引数、対象パス・URL
  2. `User Request`: ユーザー本来の依頼テキスト
  3. `User Policies`: 設定画面で定義されたポリシー
  4. `Saved Rules`: 過去に保存された承認ルール
- **遮断対象**: エージェントの内部推論全文（Chain-of-Thought）や長大な外部取得生データは一切渡さない。
- **Fail-Safe 原則**: 推論タイムアウト、エラー、出力形式不正、または確信度が低い場合は、すべて安全側（DENY）へ倒し、第3層のユーザー確認へ回す。

## 4. 第3層：マルチモーダル承認と親エージェントの仲介

### 4.1 親エージェントによる自然な仲介と没入感の維持
- **思想**:
  - 近年の高性能LLMの能力を活かし、ユーザーが「裏で動く作業エージェントの細かな内部事情」を過剰に意識させられることなく、自然な会話の文脈で作業を任せられる体験を重視する。
  - 親エージェント（頭）はユーザーの意図と文脈を理解し、作業エージェントからの報告や承認要求について、対話の中で自然にユーザーへ確認し、`send_work` を通じて作業エージェントへ指示を伝える。
- **承認要求の不変束縛（Immutable Binding）**:
  承認要求は、以下の情報を固定した不変オブジェクトとして発行される。

```rust
pub struct Approval {
    pub request_id: String,
    pub session_id: String,
    pub run_id: String,
    /// 手からの要求の場合のWorkSession
    pub work_id: Option<String>,
    /// 操作名および正規化引数のSHA-256ハッシュ
    pub action_payload_hash: Vec<u8>,
    pub tool_name: String,
    pub normalized_arguments: String,
    pub status: ApprovalStatus, // Evaluating, Pending, Approved, Denied, Expired
    pub created_at: String,
    pub resolved_at: Option<String>,
    /// 承認を束縛したクライアント
    pub client_id: Option<String>,
    pub capability: Option<String>,
    /// 表示用の外部送信先
    pub external_destination: Option<String>,
}
```
- **引数変更の無効化**: 引数が変更された場合はハッシュ不一致により旧要求を失効させる。承認は実行中のツール呼び出しにのみ適用し、別の呼び出しへ再生しない。
- Web検索の承認カードには送信先のオリジンとパスを表示する。資格情報とURLのクエリは表示用の値に含めない。未決承認の再取得でも、要求時に保存した表示用の値を返す。
- Decision API の判定中は `Evaluating` として保持し、人の確認が必要になったときだけ `Pending` に移して承認カードと未決一覧に出す。
- **束縛先はクライアントID**: 承認は`client_id`に束縛し、世代（revision）では束縛しない。カード表示後にコンパニオンのアクティブクライアントが移動しても承認は失効せず、保留中の呼び出しは移動後のクライアントへ付け替える。手からの要求は、そのWorkSessionが発注時に束縛した`client_id`に従う。

### 4.2 「頭」による代理承認と画面カード
- ユーザーへの確認が必要な場合、画面に承認カードを出しつつ、会話文脈でユーザーが「いいよ」「進めて」と許可したと「頭」が判断すれば、**「頭」が `resolve_approval` ツールを呼び出して承認を確定**できる。
- 音声承認専用の排他パイプラインや遅延STT束縛は持たず、「頭」の自然な会話判断に委ねる。
- 「頭」自身のツールが承認待ちでターンが進めないときは、同じ「頭」のモデルに新たに受け付けたユーザーの返答と保留中の操作を渡す。保留中の1件に対する `resolve_approval` だけを公開し、会話のターン内で元の呼び出しを再開する。

## 5. 「常に承認」ルールの管理と範囲限定

ユーザーが「常に承認」を選択した場合、操作の性質に応じて保存先を分ける。ただし、操作の権限（読み取り、書き込み、実行、外部送信）を越えて勝手に拡大しない。

組み込みの Web 検索は、実際の送信先 URL と検索引数に束縛して承認を保存する。送信先を含まない旧形式の検索許可は保存履歴として残り、次回は現在の送信先について許可を取り直す。

### A. 機械的な保存ルール（ホスト内ポリシー）
- **対象**: `tool_name`と`pattern`の組、および`effect`（`allow` / `confirm` / `ask_llm` / `deny`）。`pattern`が`*`なら全対象、それ以外は操作種別ごとに抽出・正規化された操作対象（ファイルパス、送信先ホスト/URL、コマンド名、MCPエンドポイント等）に対して照合し、無関係な説明文や任意文字列引数には一致させない。
- **管理**: `policy_rules`テーブルに保存し、`UpdatePolicyRules`で追加・更新・削除する。ポリシーの読み取り失敗や保存失敗は空ルールへフォールバックせず、安全側（拒否または明示エラー）へ倒す。OSカーネルによる強制ではないため、Sandbox構成ファイルやカーネル側の適用状態は持たない。
- **優先関係**: ハード禁止および保存された`deny`が最優先。`confirm`は保存された`allow`や`ask_llm`より優先し、必ず人間の確認へ回す。`allow`は能力の既定の確認要否を飛ばすだけで、ハード禁止と`confirm`は迂回できない。

### B. セマンティック・ポリシー（テキスト判定ルール）
- **対象**: 送信先ドメイン、特定コマンドパターン。
- **管理**: 構造化ルールとして保存。
- **優先関係**: 「毎回確認」に指定されている上位ポリシーがある場合、保存ルールよりも上位ポリシーが優先され、確認がスキップされることはない。

## 6. 検証条件と受け入れ基準 (Alpha Permissions Invariants)

| 不変条件 | 検証方法 | 合格基準 |
| :--- | :--- | :--- |
| **引数変更時の失効** | 承認要求発行後にエージェントが引数を改ざんして実行試行 | ハッシュ不一致により拒否され、実行されないこと |
| **「頭」による代理承認** | 承認待ち状態でユーザーが「それで進めて」と発話 | 親エージェントが `resolve_approval` ツールを実行し、保留中の操作が再開されること |
| **移動後の承認の継続** | 承認カードの表示中にコンパニオンを別クライアントへ移動してから承認 | 承認が失効せず、保留中の操作が束縛先のクライアントへ配送されること |
| **Fail-Safe遮断** | Decision Engine推論中にタイムアウト・不正JSONを注入 | 自動実行されず、必ずユーザー確認へエスカレーションされること |
