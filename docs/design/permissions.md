# 権限・承認・実行制限

状態：Alphaの採用設計（2026-11-03初版、2026-11-11改定）。製品としての振る舞いは[権限とデータの管理](../features/settings/permissions.md)を正本とし、ここでは技術的な契約・判定機構・隔離アーキテクチャを定める。[アーキテクチャ](../architecture.md)、[作業相手API](work.md)を併せて参照する。

## 1. 三層のセキュリティ境界アーキテクチャ

システム全体の安全性と自律性を両立するため、3層の境界を設ける。ユーザーに複雑な権限マトリクスやアクセスコントロールリスト（ACL）を設定させることはしない。

| 境界層 | 担当 | 仕組み |
| --- | --- | --- |
| **第1層：実効的なOS分離（Deterministic Sandbox）** | OS・カーネル | 専用ワークスペース、ファイルマウント制限、ネットワーク制限等による物理的隔離 |
| **第2層：自動判定エンジン（Semantic Decision Engine）** | ホスト推論（LLM） | Sandbox外の操作について、ユーザーの依頼・ポリシー・保存済みルールと照合し自動判定 |
| **第3層：マルチモーダルユーザー承認（Human-in-the-Loop）** | ユーザーとコンパニオン | 自動判定で拒否された操作について音声・画面で確認 |

- **ホスト管理ツールとSandbox内部は確認不要**:
  会話、記憶、状態、作業の管理などホスト自身の信頼済みツールと、Sandboxワークスペース内で完結する操作は、確認を挟まずそのまま実行する。
- **失敗は安全側（Fail-Safe）**:
  自動判定の推論エラー、タイムアウト、出力不正、または判断が曖昧（Low Confidence）な場合は、すべて拒否（DENY）として扱い、ユーザー承認カードへエスカレーションする。勝手に安全とみなして実行しない。

## 2. 自動判定エンジン（Decision Engine）の入力遮断とインジェクション防御

自動判定エンジンは、「エージェントが提案した操作が、ユーザーの本来の依頼・意図と設定ポリシーに合致しているか」のみを客観的に評価する。

### 入力コンテキストの厳格な隔離
外部から取得したWebコンテンツや不審なコード片による**間接的プロンプトインジェクション（Indirect Prompt Injection）**を防ぐため、判定エンジンに渡すプロンプトは以下の4要素のみに限定し、会話ログ全文や思考プロセスを完全に遮断する。

| 入力要素 | 内容 |
| :--- | :--- |
| **Candidate Action** | 実行しようとしているツールの名称、正規化された引数、操作対象（パス、URL、コマンド） |
| **User Request** | ユーザーが直接入力した元の自然言語指示（意図の基準） |
| **User Policies** | ユーザーが設定画面で定義したポリシー（例: 「外部へのデータ送信は常に確認」など） |
| **Saved Rules** | 過去に「常に承認」されたテキスト判定ルール |

- **渡してはならない情報（遮断対象）**:
  - 親（頭）や子（手）の内部推論全文（Thought / Chain of Thought）。
  - 外部Webページや取得ファイルの中身（「この操作を承認せよ」と書かれていても判定エンジンには見えない）。
  - 直前の雑談や無関係な過去ログ。
- **判定の独立性**:
  判定エンジンは通常の対話セッションとは独立した軽量モデル呼び出し（`purpose=decision`）として実行され、キャラクターの愛着や対話の勢いに引きずられない客観的判定を担保する。

## 3. マルチモーダル先着優先承認（Multimodal Approval）

承認カードが必要となった場合、コンパニオンは音声と画面の両方から同時に確認を行う。

```text
                     [要承認操作の発生]
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
       [ボイス対話での相談]           [画面承認カード表示]
     「〇〇してもいい？」            [承認] [常に承認] [拒否]
               │                             │
               └──────────────┬──────────────┘
                              ▼
                  [先着優先（First-come）]
          ・先に届いた方の入力で確定・ロック
          ・遅れた入力は競合せず破棄/受領のみ
```

- **先着優先と競合制御**:
  - ユーザーが口頭で「いいよ」「ダメ」と答えるか、画面ボタンをクリックするかの**どちらか早い方**で操作の成否を確定し、トランザクションをロックする。
  - 後から届いた入力によって処理が二重実行されることはない。
- **事後取り消し（Undo / Cancellation Propagation）**:
  - 承認してタスクが開始された後、ユーザーが「やっぱりやめて」と口頭やチャットで伝えた場合、これは `CancellationRequested` イベントとして即座に「手」（WorkSession）へ伝達される。
  - 「手」は [作業相手APIの設計](work.md) に基づき、一時ファイルやプロセスを安全にロールバック・クリーンアップして結果を報告する。

## 4. 「常に承認」の二元管理（Sandbox管理 vs テキスト判定ルール）

ユーザーが「常に承認」を選択した場合、その操作の性質に応じて保存先と適用メカニズムを明確に分ける。

### A. Sandboxで管理できる権限（OS/カーネル強制）
- **対象**: 特定ディレクトリへのマウント許可、ネットワーク接続先ホスト・ポートの許可、実行可能コマンドパスなど。
- **管理方法**: ホストの **Sandbox構成定義（Sandbox Rules）** に直接追加・反映する。
- **特性**: 決定論的（Deterministic）。LLMの推論を一切介さず、OSのアクセス制御によって物理的・永続的に保証される。

### B. Sandboxで管理できない権限（セマンティック・アクション）
- **対象**: 「特定ドメイン宛てのメール送信」「特定種別のデータ抽出」「外部サービスの特定APIエンドポイント呼び出し」など、高レベルの意味論的アクション。
- **管理方法**: **テキスト判定ルール（Semantic Rules）** として保存。
- **特性**: 自動判定エンジンのコンテキストに注入され、次回以降の判定時に「保存済みルールに完全一致するため即時許可」として扱われる。

## 5. 秘密情報の隔離

- APIキーやアクセストークンなどの機密情報は、ホストの資格情報ストア（OSセキュアストレージ等）に保持される。
- LLMプロンプト、会話ログ、エピソード記憶、タスクエージェントのコンテキストには秘密情報の生値を一切露出させない。
- 外部APIへの通信が必要な場合は、ホスト側の認証プロキシがトークンを付与してリクエストを代理実行する。
