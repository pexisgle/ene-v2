## 1. 目的と多層防御アーキテクチャ

システム全体の安全性と自律性を両立するため、3層のセキュリティ境界を定義する。
ユーザーに複雑なアクセス制御リスト（ACL）を設定させることなく、直感的かつ確実にPC環境を保護する。

```text
 ┌────────────────────────────────────────────────────────┐
 │ 外部・作業タスク実行（Hands / WorkSession）             │
 └───────────────────────────┬────────────────────────────┘
                             │
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第1層】決定論的 OS Sandbox（Deterministic Sandbox）  │
 │  ・専用ワークスペースへのファイルアクセス制限          │
 │  ・許可ポート・ホスト名以外のネットワーク遮断          │
 │  ・CPU / メモリ / プロセスツリー資源制限               │
 └───────────────────────────┬────────────────────────────┘
                             │ (Sandbox外操作・高権限操作の要求)
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第2層】判定パイプライン（Decision Pipeline）         │
 │  1. ハード禁止 / 毎回確認判定                          │
 │  2. 機械的保存ルール照合（パス・コマンドの完全一致）   │
 │  3. 補助的AI判定（入力遮断プロンプトによる意図評価）   │
 │  4. 実行直前の対象・引数再検証                         │
 └───────────────────────────┬────────────────────────────┘
                             │ (要確認・ポリシー抵触・AI判定DENY)
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │ 【第3層】マルチモーダル承認（Human-in-the-Loop）       │
 │  ・ボイス対話相談 ＋ 画面承認カード並行提示            │
 │  ・不変要求ID束縛 ＆ 音声承認は同時1件限定             │
 └────────────────────────────────────────────────────────┘
```

## 2. 第1層：OSネイティブSandboxと非対応環境の扱い

### 2.1 実行形態に応じたセキュリティ境界の3分類

すべてのツール・操作を一律に同一機構で扱うのではなく、実行形態に応じて保証できる境界を明確に区別する：

1. **ホスト管理ツール（Host-Provided Tools）**:
   - ホスト（Rust）自身が実行するファイル読み書きや設定操作。
   - `cap-std` によりルートディレクトリ外へのパストラバーサル（`../`）を決定論的に防止し、判定パイプライン（第2層）および `Stage::Gate` で完全に仲介・承認判定される。
2. **サンドボックス化子プロセス（Local Sandboxed Subprocess: ACP / CLI）**:
   - 外部ACPハーネスやシェルコマンド子プロセスの実行。
   - OSネイティブSandbox（Linux Landlock/bwrap、Windows AppContainer/Job Objects）によりファイルパスおよびプロセスツリーを隔離する。
   - **ネットワーク制限の強制機構（Anthropic `srt` パターン）**:
     - Landlock の `net_port`（ポート番号制御）単体では宛先ホスト名/FQDNの識別ができないため、Linuxでは **`bwrap --unshare-net`（ネットワーク名前空間の完全隔離）により直接の外部通信を物理遮断** する。
     - ただし、`bwrap --unshare-net` 下では子プロセス内のループバック（`127.0.0.1`）もホスト側から隔離されるため、ホスト上のプロキシへ直接TCP接続できない。
     - そこで、ホストとの間で共有する UNIX ドメインソケットをサンドボックス内へバインドマウントし、`ene-host` バイナリ自身の軽量サブコマンド（`ene-host internal-net-bridge --listen 127.0.0.1:PORT --connect /path/to/proxy.sock`）をサンドボックス内部で起動して中継する（外部の socat コマンド等への依存を排し、単一バイナリで完結）。
     - 子プロセスは標準の環境変数（`http_proxy=http://127.0.0.1:PORT`, `all_proxy=socks5://127.0.0.1:PORT`）を参照して通信を行い、ホスト側プロキシが宛先ホスト名・ポートを機械的ルールと照合して認可された通信のみを外部へ中継する。
     - ファイルシステムのパス制限（Landlock）は、コマンド実行直前の `Command::pre_exec` フック内で子プロセス自身に適用した上で `execve` を呼び出す。
3. **リモート外部エージェント（Remote / External Services）**:
   - クラウド上の外部エージェントやリモートサービス。
   - ホストのOS隔離は及ばないため、保証境界はConnect-RPCの入出力検証および認証トークン・認可プロファイルの範囲に限定する。
4. **クライアント端末操作（Device Capabilities）**:
   - クライアントが`ClientCapabilitySpec`で宣言し、ホストが許可した端末能力（ファイル操作、画面取得、ウィンドウ操作等）。
   - 実行実装はクライアント側にあり、ホストのOS Sandboxの外にある。しかし、**能力の許可（`granted_capabilities`）は操作単位の承認を省略する包括許可ではない**。
   - すべての`device_request`は、ホスト側の判定パイプライン（第2層）と`Stage::Gate`を通す。`ClientCapabilitySpec.approval`が`CONFIRM`の能力、ハード禁止、明示的毎回確認ポリシーに該当する操作は、`ApprovalRequest`でユーザーの承認を得るまで配送しない。
   - 承認要求は、検証済みの正規化入力・`client_id`・`activation_revision`・操作ハッシュに束縛する。クライアントが自己申告する対象説明だけを承認の根拠にせず、端末のOS権限は最終境界として別に適用する。

| OS | 主な分離機構 | 強制できる境界 | ネットワークホスト名制限の強制経路 |
| :--- | :--- | :--- | :--- |
| **Linux** | **Landlock** ＋ **bwrap / netns** | ファイルシステムパス制限、プロセスツリー制限 | 子プロセスの直接外部通信をnetnsで遮断し、ホストの**ローカル代理プロキシ経由**で許可ホスト名・ポートを決定論的検証 |
| **Windows** | **AppContainer** ＋ **Job Objects** | 専用SIDによるACLファイル隔離、CPU/メモリ制限 | AppContainerのネットワークCapabilityをローカルに限定し、ホスト代理プロキシ経由でホスト名検証 |
| **macOS** | **Apple Sandbox (Seatbelt)** | `sandbox-exec` / SBPLプロファイルによるファイル・プロセス制限 | SBPLプロファイルで外部通信を遮断し、ホスト代理プロキシ経由で通信 |

> [!NOTE]
> **ホスト名制限の強制メカニズム**:
> カーネルのポート制限（Landlock）や名前空間（netns）単体ではドメイン名/ホスト名の動的フィルタリングができないため、**子プロセスからの直接アウトバウンド通信を遮断し、ホスト自身が管理するローカルプロキシ（`http_proxy` / socks5）を経由**させる。プロキシ側で接続先ホスト名とポートを許可ルールと照合し、一致するものだけを外部へ中継する。
> ※Linuxで `bwrap --unshare-net` を使用する場合、子プロセス内のループバック（127.0.0.1）もホストから隔離されるため、ホスト側のローカルプロキシへTCP（127.0.0.1:port）では通信できない。ホストと子プロセス間で共有する UNIX ドメインソケットをサンドボックス内へバインドマウントしてプロキシ中継を行う。
> また、`cap-std` はホストプロセス（Rust）自身の安全なファイル操作（`../` パストラバーサル防止）を保証するものであり、起動した子プロセス全体のサンドボックス化ではない。子プロセスの隔離は上記OSネイティブ機構が担う。

### 2.2 Sandbox非対応環境での縮退動作（利便性優先）
古いOSカーネルや非特権コンテナ内など、環境の制約によりOSネイティブSandboxが利用できない場合：
- **動作方針**:
  - システムは処理を一律にハード拒否するのではなく、ユーザーに対して**「本環境ではサンドボックス隔離が利用できません。非隔離環境で実行しますか？」**という明示的な警告カードを提示する。
  - ユーザーが承認した場合に限り、ホスト権限で直接コマンドやスクリプトの実行を許可する。未承認の場合はタスクを安全に中断する。

## 3. 第2層：判定パイプライン（Decision Pipeline）

エージェントが提案した操作（Candidate Action）について、以下の厳格な優先順位で機械的・決定論的に検証を行い、必要な場合のみLLM補助判定へ回す。

$$\text{ハード禁止} \longrightarrow \text{明示的毎回確認} \longrightarrow \text{機械的保存ルール照合} \longrightarrow \text{LLM補助判定} \longrightarrow \text{ユーザー承認・親エージェント相談} \longrightarrow \text{実行直前検証}$$

1. **ハード禁止（Hard Deny）**: システムファイル破壊や既知の危険コマンドなど、無条件で拒否する操作。
2. **明示的毎回確認（Every-time Confirm）**: 外部送信や機密ファイル書き込みなど、設定で「必ず確認」と指定されたカテゴリ。保存ルールが存在しても優先して確認へ回す。
3. **機械的保存ルール照合（Saved Rules）**:
   - `(action_type, target)` の厳密な組み合わせで照合する（例: `/project/**` の読み取り許可が、書き込みや削除まで無断で許可することはない）。
4. **LLM補助判定（Decision Engine）**: 未登録操作の文脈適合性を評価。
5. **対話的確認（Human-in-the-Loop）**: 親エージェントがユーザーの意図を汲み取って対話的に確認・仲介。
6. **クライアント操作の対象検証**: `device_request`では、受付時の`client_id`と`activation_revision`、能力の`input_schema`、承認ハッシュを実行直前に再検証する。アクティブクライアントが切り替わっていれば`client_moved`として中止し、別端末へ配送しない。

### 3.1 入力遮断型AI判定（Decision Engine）の多層防御
- **インジェクションに対する現実的認識**:
  - Candidate Actionには、外部Webページや取得ファイルから誘導された引数（URL、コマンドパラメータ、送信メール本文等）が含まれ得るため、「プロンプトインジェクション完全防御」は成立しない。
  - したがって、AI判定は境界そのものではなく、多層防御の1要素として位置づける。
- **入力要素の限定**:
  1. `Candidate Action`: ツール名、正規化引数、対象パス・URL
  2. `User Request`: ユーザー本来の依頼テキスト
  3. `User Policies`: 設定画面で定義されたポリシー
  4. `Saved Rules`: 過去に保存された承認ルール
- **遮断対象**: エージェントの内部推論全文（Chain-of-Thought）や長大な外部取得生データは一切渡さない。
- **Fail-Safe 原則**: 推論タイムアウト、エラー、出力形式不正、または確信度が低い場合は、すべて安全側（DENY）へ倒し、第3層のユーザー確認へ回す。

## 4. 第3層：マルチモーダル承認と親エージェントの仲介

### 4.1 親エージェントによる自然な仲介と没入感の維持
- **思想**:
  - 近年の高性能LLMの能力を活かし、ユーザーが「裏で動く作業エージェントの細かな内部事情」を過剰に意識させられることなく、自然な会話の文脈で作業を任せられる体験を重視する。
  - 親エージェント（頭）はユーザーの意図と文脈を理解し、作業エージェントからの質問や承認要求について、対話の中で自然にユーザーへ確認し、`send_work` を通じて作業エージェントへ指示を伝える。
- **承認要求の不変束縛（Immutable Binding）**:
  承認要求は、以下の情報を暗号学的に束縛した不変オブジェクトとして発行される。

```rust
pub struct ApprovalRequest {
    pub request_id: String,
    pub session_id: String,
    pub run_id: String,
    /// 操作名および正規化引数のSHA-256ハッシュ
    pub action_payload_hash: [u8; 32],
    pub candidate_action: CandidateAction,
    pub status: ApprovalStatus, // Pending, Approved, Denied, Expired
    pub created_at: chrono::DateTime<chrono::Utc>,
    /// 音声承認を束縛したクライアント。端末能力の承認では必須
    pub client_id: Option<String>,
    /// 承認時の有効化revision
    pub activation_revision: Option<u64>,
    /// device_request の場合の能力名
    pub capability: Option<String>,
}
```
- **引数変更の無効化**: エージェントが操作引数を1文字でも変更した場合、ハッシュ不一致により旧要求は失効し、新しい `request_id` で再発行される（ユーザーが確認した内容と異なる操作の実行を防止）。
- **端末能力の世代束縛**: クライアント端末能力の承認は、`client_id` と `activation_revision` にも束縛する。承認後にコンパニオンが別端末へ移動した場合、旧世代の承認は失効し、新しい端末の操作へ流用されない。

### 4.2 ボイス対話と画面承認カードの協調
要確認となった操作は、音声と画面カードの両方から並行して確認が行われる。
- **先着優先（First-come）ロック**: 音声（「いいよ」「ダメ」）または画面クリックの**最初に届いた入力で承認状態を一意に確定**し、二重実行を遮断する。
- **音声承認の同時1件制限と遅延STT誤爆防止**:
  - 音声で「いいよ」と即答できる未解決の承認要求は**同時に1件のみ**とする（複数ある場合は誤承認を防ぐため画面選択を促す）。
  - **遅延確定の誤爆遮断**: 音声キャプチャ開始（発声検知）時点の未解決 `request_id` をバインドする。あわせて、承認時点の`client_id`と`activation_revision`にも束縛し、端末移動後の遅延STTが新端末の承認へ適用されないようにする。STT認識結果が遅れて確定した際、その `request_id` が既に画面クリック等で解決済み、または失効していた場合は**音声入力を即座に破棄**し、後から提示された別の承認要求へ誤って流用される事故を完全に防止する。
  - ファイル削除や外部送信を含め、すべての操作は音声でも承認可能（画面クリックの強制は行わない）。

## 5. 「常に承認」ルールの管理と範囲限定

ユーザーが「常に承認」を選択した場合、操作の性質に応じて保存先を分ける。ただし、操作の権限（読み取り、書き込み、実行、外部送信）を越えて勝手に拡大しない。

### A. 物理的Sandboxルール（OSカーネル強制）
- **対象**: パス接頭辞（例: `/home/user/project/**`）、許可ホスト・ポート。
- **管理**: ホストのSandbox構成ファイルに直接追加。
- **操作種別の限定**: パスの追加であっても、許可された操作種別（`read_only` / `read_write`）を厳格に保持する（読み取りを常に許可したからといって、書き込みや削除まで無断許可されることはない）。

### B. セマンティック・ポリシー（テキスト判定ルール）
- **対象**: 送信先ドメイン、特定コマンドパターン。
- **管理**: 構造化ルールとして保存。
- **優先関係**: 「毎回確認」に指定されている上位ポリシーがある場合、保存ルールよりも上位ポリシーが優先され、確認がスキップされることはない。

## 6. 検証条件と受け入れ基準 (Alpha Permissions Invariants)

| 不変条件 | 検証方法 | 合格基準 |
| :--- | :--- | :--- |
| **引数変更時の失効** | 承認要求発行後にエージェントが引数を改ざんして実行試行 | ハッシュ不一致により拒否され、実行されないこと |
| **音声承認の単一性** | 2件の承認待ちがある状態で「いいよ」と音声発話 | 音声による一括誤承認を行わず、画面での選択を促すこと |
| **遅延STTによる誤承認防止** | 要求Aの承認発話テキストが、要求A失効後かつ要求Bの提示後に遅延到着 | `speech_start_request_id` の不一致により要求Bへの誤適用が防止され、安全に破棄されること |
| **Sandbox非対応環境の明示警告** | 分離機構が利用できないモック環境でコマンド実行を要求 | 無断で実行せず、非隔離環境である旨の警告カードを提示してユーザーの承認を求めること |
| **先着優先排他ロック** | 音声承認と画面拒否ボタンをミリ秒単位で同時送信 | 先着した一方のみで状態がロックされ、二重実行や競合破壊が起きないこと |
| **Fail-Safe遮断** | Decision Engine推論中にタイムアウト・不正JSONを注入 | 自動実行されず、必ずユーザー確認（DENY）へエスカレーションされること |
| **端末能力の操作単位承認** | `approval = CONFIRM`の能力で`device_request`を実行 | 能力の許可だけで素通しせず、`Stage::Gate`と`ApprovalRequest`を経ること |
| **端末切替後の失効** | 承認後にアクティブクライアントが切り替わり、旧`activation_revision`で操作結果・音声入力・承認を送信 | 旧世代の入力がすべて破棄され、新クライアントの状態を変更しないこと |
