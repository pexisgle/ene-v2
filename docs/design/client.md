# クライアントと音声・知覚・身体表現の設計

この文書では [用語集](../terms.md) と [全体アーキテクチャ](../architecture.md) を前提に、すべてのクライアントへ共通する `端末能力` の連携・「目」（知覚）・「体」（身体表現）・音声対話・複数コンパニオンの調停、および端末切り替え時の大まかな挙動をまとめます。
ホストは特定の描画エンジン・OS・音声デバイスを前提としないため、具体的な OS API や描画・音声ライブラリの実装詳細は各クライアントおよびプラグインの実装コードへ譲り、利用面の仕様は [対話と音声](../features/interaction.md) と [作業と拡張](../features/tasks.md)、通信定義やプラグイン契約は [ホスト API](../api.md) と [プラグイン拡張](plugins.md) を参照する構成です。

## 端末能力の宣言と操作配送の境界

クライアントは接続時に、身体表現・画面やファイル操作・知覚監視など自身の端末で実行できる機能と入力形式や表現の選択肢を `端末能力` としてホストへ宣言し、次の図の境界で連携します。

```text
+---------------------------------------------------------------------------+
| クライアント（端末固有の表現エンジン・知覚センサー・音声入出力）          |
|  ・接続時に利用可能な `端末能力` と表情・モーション選択肢を宣言           |
+-------------------------------------+-------------------------------------+
                                      | Connect-RPC
                                      | （能力宣言／端末操作／知覚／音声）
+-------------------------------------v-------------------------------------+
| ホスト（「頭」・確認制御・記憶・作業オーケストレーション）                |
|  ・ホスト自身の能力（ホスト側ファイル操作など）を提供                     |
|  ・許可された `端末能力` を公開し、確認境界を通してアクティブ端末へ配送   |
+---------------------------------------------------------------------------+
```

ホストはホスト側のファイル操作など自身の能力も提供しつつ、クライアントから宣言された能力のうちそのクライアントへ許可した範囲だけを公開して「頭」や「手」の操作へ組み込み、端末側の描画・検知・操作は現在アクティブなクライアントへ要求を配送する設計です。
能力の宣言は機能の有無を示すだけに留め、確認が必要な操作の呼び出しには [作業実行の設計](work.md) に基づく判定と承認を必ず通したうえで、接続断を挟んだ再送時にもクライアント側で同じ操作を重複実行しない規則です。

## 「目」（知覚）の収集と選別

クライアントの「目」は既定をオフとし、その端末で有効化されているときだけ前面ウィンドウの変化や操作・離席状態、対応環境での画面情報を収集してホストへ送り、画面ロック中や取得手段のない環境では停止して取得できない情報を推測で補いません。
エディタ上の作業対象やブラウザの閲覧先といった詳細な文脈は表層的なウィンドウ名だけに頼らずクライアント側の専用連携プラグインから補い、ホスト側でも `作業セッション` の状態と照合したうえで、そのままの観測事実とクライアントまたはホストが状況を解釈して作る知覚要約を区別して扱います。
ホスト側の「目」は直近の観測から意味のある変化や監視条件への一致だけを選り分けて応答生成時にメモリ上だけで組み立てる一時文脈へ届けつつ、画像と知覚要約は会話ログへ保存しない方針とします。

## 「体」（身体表現・リップシンク・デスクトップ演出）

アバターの描画やモーション再生はクライアント側の表現エンジン（デスクトップ標準構成ではクライアント本体と疎結合に分けた描画用別プロセス）が担い、ホストは描画ライブラリやモデル形式に依存しない構成です。
「頭」は発話の有無にかかわらず単独で表情や仕草を指示し、クライアントは未対応の動きを無視または近似して会話や音声を止めずに滑らかに切り替え、ウィンドウの縁へ腰掛けるなどのデスクトップ演出もウィンドウ位置を取得できない環境では画面端への固定などへ安全に縮退します。
リップシンクはホスト側との往復遅延や通信の詰まりを招かないようクライアント側で再生音声に合わせて口の動きを合わせる仕組みです。

## 音声対話の基本方針

音声対話は当面ターン制を基本としながら将来の全二重に近い機能拡張を見据えて詳細な構成を固定しない方針とし、思考過程や「手」の内部出力・`記憶の整理`・`会話の圧縮` を除いた「頭」の発話本文だけを音声化して応答します。
音声出力はアクティブなクライアントが単独で所有して再生デバイスの音声形式への変換も受け持ち、割り込みや新しい発話へ切り替える際は古い音声を停止して重ならないよう保ちつつ、マイクへのスピーカー音混入の抑制は OS やクライアント側環境に期待し、音声入力による操作の承認も通常の対話と同様に受け付ける前提です。

## 複数コンパニオンの調停とアクティブ端末の切り替え

複数のコンパニオンを同時に動かす際は音声認識の結果を名前で事前に絞り込まず全員へ同報配信し、各自が自分の人格や会話文脈に照らして自分宛てかを判断し、無関係であれば応答せず静観します。
発話権は最初に応答を始めた 1 体へ先着で与えて競合した側の推論を即座に破棄し、会話ターン終了と発話完了の同報で次の掛け合いへつなげる一方、同じ利用者発話に基づく作業の着手はホスト側が先着 1 体へ原子的に割り当てて外部操作の多重実行を防ぐ仕組みです。
アクティブ端末を別のクライアントへ切り替えた瞬間は旧端末の音声再生と音声出力の所有を即時に終えてホスト上の発話権も解放し、旧端末から遅れて届く音声入力や知覚イベントを破棄して新端末へ旧端末の未再生分を引き継がず、一時的な切断と区別して旧端末の再接続でも過去の発話状態を復活させません。
