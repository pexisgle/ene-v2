# コンテキスト圧縮（Compaction）とセッション管理詳細設計

状態：Alphaの採用設計（2026-11-11策定）。[全体アーキテクチャ](../architecture.md)、[技術スタック](tech-stack.md)、[心と自動記憶](mind.md)、[チャット機能仕様](../features/chat/README.md)を参照する。

---

## 1. 目的と設計原則

デスクトップ常駐AIコンパニオンとして無期限・長時間の対話を破綻なく継続するため、LLMのコンテキストウィンドウ枯渇を防止しつつ、過去の対話の文脈を失わない持続性を担保する。

### 基本原則
1. **会話の正本（永続ログ）とプロンプト用ビューの分離**:
   - 会話の生ログは追記型（Append-only）の線形ログとしてディスクに完全保存され、改ざん・物理削除されない。
   - Compactionによる要約は、LLMへ送信する「アクティブプロンプト窓（View）」の構築時のみに利用される。
2. **安全マージンを設けたコンテキスト上限検証とフォールバック**:
   - 閾値による目安だけでなく、送信直前にすべての構成要素（ツール・人格・記憶・履歴・動的文脈）のトークン合計を検証する。プロバイダーのusageに基づく安全推定マージン（10%）を確保し、万一プロバイダー側で上限エラーが生じた場合も回数制限付きの安全な切り詰めフォールバックを備える。
3. **KVキャッシュ（Prefix Caching）の最大化**:
   - 毎ターン変動する情報（日時・知覚要約）をプロンプトの末尾側に配置し、静的設定および過去ログの高いキャッシュヒット率（ターゲット: >90%）を目指す。
4. **割り込み耐性と会話テンポの最優先**:
   - バックグラウンド要約処理の遅延や失敗によって、ユーザーへの発話応答を待たせない。

## 2. 会話ログの構造（Rig の会話管理と rig-memory の活用）

独自の会話ログ型や同期用の中間構造体を新設して変換オーバーヘッドを作るのではなく、**`rig-ecs` のセッションログ機構（`SessionLogPlugin` + `SqliteSessionStore`）と `rig-memory` の要約機構（`SummaryState` / `apply_summary`）を直接の正本**として採用する。

### 2.1 正本と責務の明確な分離
- **Rig（`rig-ecs` / `rig-memory` / `rig-sqlite`）が所有する正本**:
  - **会話履歴の正本**: `rig::sqlite::SqliteSessionStore`（`rig-sqlite`）により、会話ログ（`SessionLog`）のメッセージ列（マルチパート、ツール呼び出し、プロバイダーメタデータ）を単一の SQLite データベース（`host.sqlite3`）内に完全保持。ファイルシステム上の追記ログ（`DirStore`）との二重管理やクラッシュ時の2相復旧を完全排除する。
  - **要約状態と圧縮範囲**: `rig-memory` の標準構造（`Anchor` によるターンの起点アンカー、`SummaryPlan.keep_from`、適用後の置換情報を記録する `Compacted`、および `summary_state`）が要約テキストと置換範囲を管理し、`apply_summary` によって会話ログ内に直接反映。外部テーブルへの二重保存は行わない。
- **ene-host が管理する追加状態**:
  - `companion_id`（コンパニオンとセッションの対応付け）
  - `InactivityTracker`（厳密なユーザー無操作アイドル時間の計測）
  - `processed_turns_cursor`（SQLiteへの長期エピソード記憶抽出の進捗位置）
- **表示用プロジェクション（View）**:
  - クライアントAPI等で会話履歴を外部へ提供する構造体（`ConversationView` / `MessageView`）は、正本ではなく `SessionLog` からオンデマンドで生成される**読み取り専用ビュー（Projection View）**として位置付け、ene側で可変状態として二重管理しない。

## 3. アイドル検知とCompaction発動条件

### 3.1 厳密なユーザーアイドル検知（InactivityTracker）
- **判定基準**:
  - アイドルタイマーのリセット契機は、**「ユーザーからの明示的な発話・チャット入力、または承認アクション」の受信時のみ**とする。
  - コンパニオン自身による自発的な独り言・見守り発話・スケジュール実行などのキャラクター側の発話は、アイドルタイマーを**リセットしない**。

```rust
pub struct InactivityTracker {
    pub last_user_interaction_at: std::time::Instant,
}

impl InactivityTracker {
    pub fn on_user_activity(&mut self) {
        self.last_user_interaction_at = std::time::Instant::now();
    }

    pub fn idle_duration(&self) -> std::time::Duration {
        self.last_user_interaction_at.elapsed()
    }
}
```

### 3.2 発動トリガー（ソフト閾値とハード強制閾値）
- **ソフト発動（バックグラウンド非同期）**:
  - トークン使用率が **65%〜75%** を超過し、かつユーザーのアイドル時間が **60秒** 以上継続した場合に発動。通常のターン進行中は現行の要約スナップショットと直近履歴を用いて即座に応答し、会話テンポを阻害しない。
- **ハード強制閾値（緊急窓切り詰めと会話テンポ優先）**:
  - ユーザーが休まず連続対話してアイドルが一度も訪れず、トークン使用率が **85%〜90%** に達した場合、数秒〜十数秒のLLM同期要約でユーザーを待たせて会話テンポを破壊することは行わない。
  - 代わりに、**直ちに `rig_memory::recent::view` による緊急窓切り詰め（最古の完全ターンをプロンプト窓から一時除外）を優先適用して即座に応答を返しつつ、バックグラウンド要約タスクをディスパッチ**する。
  - ディスク上の追記型会話正本（`SessionLog`）は一切削除されず保持されるため、次回の無操作時にバックグラウンド要約が完了すれば、`Compacted` として正式にログへ反映され、永続ログ・プロンプト窓の双方が完全な整合性へ収束する。

## 4. 非同期バックグラウンド要約とノンブロッキング対話

Compaction（要約生成）は、会話の進行を妨げない非同期バックグラウンドのサイドLLM呼び出し（`rig_memory::Summarizer`）として実行される。

```text
[対話進行中] ──→ (アイドル検知 or 窓溢れ) ──→ [バックグラウンド要約タスク起動]
      │                                                │
      │ (割り込みなし)                                 │
      │                                                ▼ [正常完了時]
      │                                         [Summary (Compacted) を安全に更新]
      │                                                │
      │                                                ▼ (次ターンから新要約適用)
      ▼ (ユーザーからの割り込み発話)                   │
[通常通り会話ログに即時追記]                           │ (割り込み検知)
      │                                                ▼
      ├─────────────────────────────────────────→ [進行中要約タスクを即座にキャンセル・破棄]
      ▼                                           [次回アイドル時へ再延期]
[現行窓 (直前スナップショット要約 + 直近ログ) で即座に応答]
```

### ノンブロッキング継続の仕組み
1. **正本の無停止追記と通常ターンの即時応答**:
   - 会話の正本（`SessionLog` / `SqliteSessionStore`）は常に完全な線形追記モデルを維持する。通常ターンでは、バックグラウンド要約タスクの稼働状態にかかわらず、現行のプロンプト窓（前回の完了要約スナップショット ＋ 直近のメッセージ列）を用いて即座に推論を開始し、ユーザーへの応答テンポを維持する。
2. **割り込み時の安全な要約破棄と即時応答**:
   - バックグラウンド要約の実行中にユーザーが発話した場合、ホストは現在の最新要約（前回の完了スナップショット）と直近メッセージを用いて即座に推論し、遅延なく応答を返す。
   - **実行中だった要約タスクは安全にキャンセル・破棄され、次回のアイドル時間へ延期**される。要約途中の古いスナップショットが遅れて届いて新しい発話ログと競合したり、不整合なオフセットで適用されるリスクを排除する。
   - これにより、割り込み時も即座に対話が継続し、次回の無操作時に最新の会話文脈を反映したクリーンな要約が再スケジュールされる。
3. **ハード閾値時の会話テンポ優先（緊急窓切り詰め）**:
   - アイドルが訪れずハード閾値（85%〜90%）を超過した場合でも、同期要約による長時間の会話停止は行わず、§5.2 の緊急窓切り詰めを適用して即座に応答を生成する。

## 5. 機械的コンテキスト上限検証とフォールバック（`rig-memory` 標準機能の活用）

### 5.1 過大な単一入力の入口遮断（Ingress Limit）
- **受信時の即時検証**:
  - `SendMessage` APIの受付時点で、入力テキストのサイズ・トークン数（上限: **8,000トークン / 約32,000文字**）を検査する。
  - 1件の入力だけでモデルのコンテキスト窓を破綻させるような過大な入力は、**そもそも会話ループに受け付けず、即座に明示的エラー（`InputTooLargeError`）を返して拒否**する（勝手な末尾切り捨ては行わない）。

### 5.2 送信直前の機械的検証と窓切り詰め（Window Trimming）
モデルへのリクエスト送信直前（`PrepareSystems::Fit`）に、ホストは `rig-memory` の標準ユーティリティ関数と以下の安全条件を機械的に検査する：

$$\text{next\_request\_tokens} + \text{OUTPUT\_MARGIN} \le \text{Model Context Limit}$$

- **`Anchor` / `RequestStart`**: 前回応答でプロバイダーが報告した実トークン使用量（Usage）と対象メッセージ位置を `Anchor` として保持し、`RequestStart` からの差分計算の起点として `next_request_tokens` を正確に評価する。
- **`OUTPUT_MARGIN`**: モデルの最大出力長（例: 4,096トークン）に安全マージン（10%）を加算した予約枠。
- **`ClearToolOutputs`**: コンテキスト圧迫時、過去ターンの肥大化した巨大ツール出力（長大なファイル全文等）を安全に省略プレースホルダーへ置換し、会話の骨格を破壊せずにトークンを削減。
- **`recent::view`**: それでも上限を超える場合、最古の完全ターン単位（User ＋ Assistant または ToolCall ＋ ToolResult の完全な往復）でアクティブプロンプト窓から一時除外（ToolCallとToolResultを分断する切り詰めは禁止）。プロンプトのContext枠に `[System Notice: 過去の一部ログを一時的に省略して対話を継続しています]` を付与する。
- **履歴全除外でも収まらない場合の明示的失敗（ContextExceededError）**:
  - 削れる過去履歴をすべて除外してもなお、「固定部分（ツール定義＋ペルソナ）＋ 今回の入力 ＋ OUTPUT_MARGIN」がモデルのコンテキスト制限を超過している場合、**上限に収まらない要求をモデルへ送信せず、直ちに `ContextExceededError`（文脈上限超過エラー）を返す**。
  - 無理な送信によるモデルプロバイダー側の400エラーや勝手な末尾文字化けを防止し、ユーザーへ「入力情報またはシステム設定がモデルの許容上限を超えているため処理できません」と誠実に通知する。

## 6. プロンプト構築順序（Prefix Caching 最適化）

Anthropic Claude、OpenAI、Geminiの **KVキャッシュ（Prefix Caching）** ヒット率を最大化するため、キャッシュ境界を壊さない「静的先・動的末尾」の順序を厳格に維持する。

> [!CRITICAL]
> **動的情報の配置とキャッシュ保護**:
> OpenAI Responses API や Anthropic Messages API では、`SystemPrompt` はメッセージ列の最先頭に集約される。
> もし `SystemPrompt` 内に毎ターン変化する動的要素（Pinned Memory、想起記憶、現在の心、現在日時）を含めてしまうと、**その後ろに続く会話履歴全体のPrefix Cacheが無効化**されてしまう。
> したがって、システムプロンプトには完全な静的情報のみを配置し、変動情報はすべて `PrepareSystems::Edit` で `ModelRequest.history` 末尾の最新ユーザー発話メッセージ（`User_N`）内にブロックとして結合する（Dynamic Tail）。

```text
 ┌────────────────────────────────────────────────────────┐
 │ 【SystemPrompt / 静的プレフィックス】 (完全不変)        │
 │  1. Tools Definition (ツールスキーマ・セッション間共通) │ ── セッションを超えて
 │  2. System Persona & Core Profile (作者設定・世界観)   │    高キャッシュヒット率！
 │  3. Static User Profile (ユーザーの基本呼称・設定)      │    (Target: >90%)
 ├────────────────────────────────────────────────────────┤
 │ 【Conversation History】 (追記型・低頻度更新)          │
 │  4. Compaction Summary (過去の要約テキスト)            │ ── 過去ログ全体が
 │  5. Recent Dialogue History (直近の会話生ログメッセージ)│    キャッシュヒット対象
 ├────────────────────────────────────────────────────────┤
 │ 【Dynamic Tail Context in User_N】 (非永続・動的末尾)   │
 │  6. Pinned Core Memory (重要度10の中核事実)            │
 │  7. Recalled Memories (今回想起された関連エピソード記憶)│ ── 毎ターン変動する情報は
 │  8. Current Mind State (現在の感情・関心事)            │    SessionLog には書き込まず
 │  9. Perception Summary (目の知覚要約・開いている画面等) │    Fit時にインメモリ注入！
 │  10. Current Timestamp (現在日時)                      │
 ├────────────────────────────────────────────────────────┤
 │  11. Latest User Speech (今回のユーザー発話本文)        │
 └────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **動的文脈の非永続インメモリ注入（SessionLog の汚染防止）**:
> 6〜10の動的コンテキスト（Pinned Memory、想起記憶、現在の心、知覚要約、現在日時）は、**`SessionLog` へは一切書き込まない**（`DeliveryMode::Inform` 等で永続ログに混ぜてはならない）。
> `PrepareSystems::Edit` で `ModelRequest.history` 末尾の最新ユーザー発話メッセージ（`User_N`）内にインメモリで結合（先頭または末尾ブロック）した上で、**`PrepareSystems::Fit` を動的文脈を含む要求全体に対して実行**し、合計トークン数を評価した上で履歴ウィンドウ（`recent::view`）を切り詰める。
> これにより、動的文脈を含めた完全な要求がモデル上限に収まることを保証しつつ、`SessionLog` には純粋な会話ログのみが記録され、`GetHistory` APIに内部コンテキストJSONが漏洩したり、増分記憶整理（Consolidation）が自らの想起記憶を再学習する自己汚染ループを根本から防止する。

## 7. 検証条件と受け入れ基準 (Alpha Compaction Invariants)

| 不変条件 | 検証方法 | 合格基準 |
| :--- | :--- | :--- |
| **厳密なアイドル判定** | コンパニオンの自発独り言や定期tickを連続発生させる | ユーザー入力がない限りアイドルタイマーがリセットされず、経過時間通りにCompactionが発動すること |
| **過大入力の即時遮断** | 8,000トークンを超える単一テキストをSendMessageで送信 | 会話ループに入らず即座に `InputTooLargeError` が返され、メモリや窓を圧迫しないこと |
| **割り込み即時応答** | バックグラウンドCompaction中にユーザー発話を入力 | Compaction完了を待たずに直前スナップショットから推論リクエストがディスパッチされ（ディスパッチ遅延 500ms以内）、実行中結果が安全に破棄されること |
| **機械的上限検証とフォールバック** | 長大テキストを入力し、要約APIをタイムアウトさせる（通常ケースと履歴枯渇ケース） | 削れる過去履歴があればターン単位で切り詰めて応答を返し、全履歴を除外しても収まらない場合はモデルへ溢れリクエストを送信せず `ContextExceededError` を返すこと |
| **Prefix Cache保護** | 同一セッションで連続発話し、プロバイダーのキャッシュ使用量を検証 | 過去会話履歴のプレフィックスがキャッシュヒットし、入力トークン課金・レイテンシが削減されること |
