# 作業実行・操作確認・接続保護の設計

この文書では [用語集](../terms.md) と [全体アーキテクチャ](../architecture.md) を前提に、「頭」から「手」への作業委譲と `作業セッション`・`実行ターン` の制御、スケジュール稼働、操作の 3 段階確認境界、およびホスト接続のアクセス保護に関する設計規則と契約をまとめます。
具体的な型名・モジュール構成・バージョン情報は実装コードへ譲り、利用面の狙いは [作業と拡張](../features/tasks.md) と [接続と設定](../features/setup.md)、通信メッセージ定義やプラグインの詳細契約は [ホスト API](../api.md) と [プラグイン拡張](plugins.md) を参照する構成です。

## 「頭」と「手」の役割分離と作業の単位

内部では対話と判断を担う「頭」と実務を進める「手」を分けても利用者にとっては同一のコンパニオンであるため、「頭」が常に一人称で報告する一方で、実務管理は文脈を保持する `作業セッション` と 1 回の指示を区切る `実行ターン` に寿命を厳格に分離します。
「手」の実行主体は会話ターンから独立して動作するため発話の割り込みが進行中の作業を止めず、ホスト内蔵の「手」は `作業セッション` ごとに 1 体を維持する一方、外部の ACP ハーネスはプラグイン境界の内側でアダプターごとに同時 1 セッションだけを動かしてホスト再起動時の未完了ターンを失敗として確定する設計です。
「手」の本体は進捗・完了の報告と `端末能力` の呼び出しだけを備えて実務手段を MCP・Wasm プラグイン・ACP で後から足す最小構成とし、「頭」からは自然言語の指示と必要な作業手順だけを引き継いで `記憶` や `人格設定` の書き換え権限は持たせません。
進捗報告やイベントに載せるセッションと実行ターンの識別子は LLM の引数に書かせずホストの実行文脈から自動で束縛し、終了済みの古いターンから遅れて報告が届いても監査記録にとどめて後続ターンの状態は上書きしない規則です。

## 実行制御・即時中断・スケジュール稼働

実行中の作業から活動報告が既定で 90 秒間途絶えた場合は、「頭」へ返答を強制しない状況通知を 1 回だけ差し込んで重複警告を抑え、新たな報告が届いた時点で経過時間と警告済みの印を戻します。
`作業セッション` への追加指示は実行中であれば現在の作業キューへ積み、待機中であれば同じセッション内で新しい `実行ターン` を始める統一経路とし、同じ冪等性キーと同じ内容の再送には会話ログの付帯記録と照合して元の受付結果を返し、内容が異なる再送は競合として拒否する仕組みです。
作業の中断は会話からの指示でも緊急停止操作でも同じ経路で直ちに確定させ、保留中の承認要求を消してセッションを待機へ戻しつつ OS のプロセスグループまたは Job Object 管理で子プロセスだけを回収し、ローカルの巻き戻しは保証せず送信済みメールやクラウド資源作成など取り消すことができない外部操作もそのまま正直に報告して成否不明な操作の自動再送は行いません。
周囲の変化を拾う「目」とは別に、「頭」は単発または定期の予定をホストの現在時刻基準で登録・一覧・解除して発火時刻に指示を自身の入力キューへ投入し、単発予定は実行後に無効化しながらクライアント不在時も自律稼働を継続して端末操作や確認判断だけを保留する仕組みです。

## 操作の安全確認と 3 段階の判定境界

操作の安全確認には標準の判定モードと全操作を確認なしで進める `FullAccess` モードがあり、サンドボックスによる実行隔離を必須の前提とせず標準モードにおける次の 3 段階の判定流れを安全境界の基本とします。

```text
+-------------------------------------------------------------------+
| 作業ツール・外部送信・`端末能力` の呼び出し要求                   |
+---------------------------------+---------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
| 【第 1 段階】機械的な判定                                         |
|  ・ハード禁止（即拒否）／ 毎回確認（第 3 段階へ直行）             |
|  ・安全なホスト内操作・保存済み「常に承認」ルール（即許可）       |
+---------------------------------+---------------------------------+
                                  | 未登録または LLM 判定対象
                                  v
+-------------------------------------------------------------------+
| 【第 2 段階】LLM 補助判定（長さと件数を制限した入力）             |
|  ・依頼文脈・`自由文ポリシー`・保存ルールの基準で安全性を評価     |
+---------------------------------+---------------------------------+
                                  | 危険・ポリシー抵触・障害・時間切れ
                                  v
+-------------------------------------------------------------------+
| 【第 3 段階】利用者承認（未許可の要確認操作のみ）                 |
|  ・承認カード、または「頭」による会話文脈からの代理承認           |
+-------------------------------------------------------------------+
```

判定では金融決済などの禁止領域・重要なシステム領域の変更・破壊的コマンド・危険な検索先を無条件で退けるハード禁止を最優先とし、毎回確認指定・パスや URL やコマンド名など正規化済み対象への保存ルール照合・LLM 補助判定・利用者承認の順に処理し、外部送信を伴う組み込み機能や MCP・Wasm プラグイン・`端末能力` も例外なくこの 3 段階の判定を通過します。
プロンプトインジェクションへの多層防御として LLM 補助判定へ渡す情報は、長さと件数を制限した候補操作（ツール名・操作対象・正規化引数）、直近の依頼本文、1 件あたり最大 500 文字の `自由文ポリシー`、およびツール名と対象パターンと判定種別だけを抜き出した保存ルールに限定して内部推論全文や長大な外部取得生データを遮断し、15 秒のタイムアウト・エラー・出力不正・低確信度はいずれも安全側として第 3 段階の利用者確認へ倒す設計です。

## 承認の不変束縛・代理承認・保存ルールの優先関係

承認要求は操作名と正規化済み引数の SHA-256 ハッシュを固定して発行し、実行直前に引数が変わっていればハッシュ不一致で要求を失効させ、1 つの承認を別の呼び出しへ再利用しません。
承認と `端末能力` の呼び出し先はクライアント識別子へ束縛するため、承認カードの表示中にアクティブ端末が切り替わった場合も承認を失効させずに保留中の操作を新しいアクティブ端末へ引き継ぎます。
確認の負荷を抑えるため承認カードは第 1・第 2 段階を通過しない未許可の要確認操作に限って提示しつつ、カード操作だけでなく利用者が会話の中で許可したと「頭」が判断した場合に承認を代行する仕組みや、会話で得た許可条件を `自由文ポリシー` へ自動で追記する流れを備えた設計です。
「常に承認」を選んだ保存ルールも読み取り・書き込み・実行・外部送信といった権限区分を越えて適用範囲を広げず、優先順位は「ハード禁止および保存済み拒否 ＞ 毎回確認 ＞ 保存済み許可・LLM 補助判定」を保ち、ルールの読み込みや保存に失敗した場合も空ルールへ切り替えず安全側で拒否または明示エラーを返します。

## ホスト接続とアクセス保護境界

ホストは個人所有を前提としてアカウント・ロール・端末別の管理権限を自作せず許可済みクライアントへ同等の操作権を与える一方、接続できることと端末操作・外部送信の許可判定は別の責務として切り離し、次の表の条件を満たす接続経路だけに到達を限定します。

| 経路 | 保護境界 | 要件と制限 |
| --- | --- | --- |
| ローカル | 同一 OS 利用者の保護領域・制限付きローカルソケット | 共有マシンではループバック接続単独を同一利用者認証とみなさず、同一マシン上の利用者を全員信頼できる環境だけに許容する |
| `Tailscale Serve` | Tailscale による接続元認証とアクセス制御 | アクセス制御で意図した主体だけに到達を限定し、インターネット公開の `Funnel` は使わない |
| `Cloudflare Tunnel` + `Access` | 保護された Access アプリの認証・認可 | Tunnel 単体を利用者認証とみなさず Access 保護と組み合わせ、可能な構成では Access JWT 検証も有効化する |
| その他のプロキシ | 外部認証と到達制限を備える安全経路 | 認証・暗号化・到達制限・失効方法が確認できる経路だけを許容し、基準を満たさないものを保護なしの接続経路として使わない |

無保護のままインターネットや無制限のローカルネットワークへは待ち受けず、ローカル HTTP サーバー側でも同一端末ブラウザからの不正アクセスを防ぐために `Host` および HTTP/2 権限部がループバックまたは明示許可済みの接続先に一致することを確認し、予期しない外部 `Origin` を遮断しつつ状態と実行用ディレクトリの権限保護および単一ホストの排他ロックを保つ方針です。
外部のアクセス制御へ認証を完全に引き渡す構成は未実装であるため、到達制限と取り消し条件を実機で確認して無保護経路がないと確かめられるまでは現行の `Owner Bearer` 認証を必須として維持し、保護できない環境で無認証の公開へ切り替えることはしません。
外部の接続サービスで障害が起きた場合もローカル環境での利用とホスト上の作業・スケジュール稼働は影響を受けずに継続する構成を保ちます。
