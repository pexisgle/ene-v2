# プラグイン・拡張アーキテクチャ（Everything is a plugin）

状態：Alphaの採用設計（2026-11-11策定）。[全体アーキテクチャ](../architecture.md)、[機能の拡張](../features/extensions/README.md)、[作業相手API](work.md)、[知覚・音声](voice-avatar.md)、[デスクトップクライアント](desktop-client.md)、[権限・Sandbox](permissions.md)を参照する。

---

## 1. 設計思想：Everything is a plugin

eneにおける拡張性は、単なる「外部APIツールの追加」にとどまらない。デスクトップ常駐AIコンパニオンとしての全方位の能力をプラグインとして拡張・差し替え可能にする **"Everything is a plugin"** を設計原則とする。

システムを「頭」「手」「目」「体」の4つの境界に整理し、このうち **「手」「目」「体」の3つを主要なプラグイン拡張ポイント** として開放する。

| 拡張ポイント | 役割 | プラグインの形態 |
| :--- | :--- | :--- |
| **「手」の拡張（Actions & Tools）** | 実務タスク遂行、外部操作 | MCP（`rig-rmcp`）、ACP外部タスクハーネス（WasmはPhase 2） |
| **「目」の拡張（Perception Sensors）** | クライアント環境の知覚、状況認識 | クライアント側センサープラグイン（IDE連携、ブラウザ監視拡張、OSイベントフック、アクティブウィンドウWatcher） |
| **「体」の拡張（Body & Expressions）** | クライアント側の身体表現、デスクトップ演出 | クライアント側表現プラグイン（VRMAアニメーション、ブレンドシェイプ表情プリセット、デスクトップギミック（座る、窓押し等）） |

---

## 2. 三大拡張ポイントの技術仕様

### 1. 「手」の拡張（Actions & Tools）
作業エージェント（Hands / WorkSession）が実務タスクで使用するツールや実行基盤の拡張。
- **MCP（Model Context Protocol）接続（`rig-rmcp`）**:
  - 業界標準のMCPプロトコルに基づき、公式の **`rig-rmcp`**（`McpConnection` / `ManagedToolSink`）または `rig_mcp_client::McpCorePlugin` を採用。
  - 設定DBで認可されたMCPサーバーのみをコード側から明示的に接続・再接続管理し、取得されたツール定義を `world.spawn_tool` で「手」へ提供する（自前のJSON-RPCハンドラ自作を排除）。
- **ACP（Agent Client Protocol）外部ハーネス**:
  - 特化型のエージェント実行環境（例: 高機能コーディングハーネス）をACP経由で接続し、一連のタスク実行をまるごと委託可能。
- **Wasmプラグイン（Extism組み込み: Phase 2 拡張フェーズ）**:
  - 安全にサンドボックス化されたWebAssemblyプラグイン。Alpha/Minimal構成ではノイズを排すため対象外とし、後続フェーズでCapability制限付きランタイムとして段階的に導入する。

### 2. 「目」の拡張（クライアント側 Perception Sensors）
知覚センサーはクライアント環境に固有の責務であり、ホストは受信したイベントの要約とコンテキスト注入に専念する。
- **センサープラグインの責務（クライアント側）**:
  - OSや各種アプリケーション（VS Code、Chrome、端末エミュレータ等）からのイベントを購読、または定期サンプリングを行い、生のイベントデータを`ClientService.ReportPerception`でホストへ送信する。
  - センサーの実装方式（OSネイティブフック、IDE連携、ブラウザ拡張、APIポーリング等）はクライアントが選び、ホストは関知しない。
  - ホストはこれを受信し、簡潔な知覚要約（Perception Summary）に変換して「頭」の動的文脈枠へ注入する。
- **動的Watcher対応と能力宣言**:
  - 動的監視を受け付けられるクライアントは、`eye.watch`を`ClientCapabilitySpec`で宣言する。ホストはこの能力を宣言し許可されたアクティブクライアントにだけ`set_eye_watch`ツールを公開し、`DeviceOperation`で監視条件を配送する。
  - クライアントは自身のセンサー実装で監視条件をリアルタイム評価し、合致時に優先割り込み通知（Priority Interrupt）を`ReportPerception`で返す。
  - クライアント側プラグインはホストのフック機構とは独立して動作し、`ReportPerception`と`DeviceOperation`の境界でのみホストと接続する。

### 3. 「体」の拡張（クライアント側 Body & Expressions）
アバター表現やデスクトップ演出はクライアント側の表現エンジンとプラグインが担う。
- **VRMAモーション・表情パッケージ（クライアント側）**:
  - 新たな待機モーション（Idle）、相槌モーション（Nod）、喜び・驚きなどの感情アクション、身振り手振りをクライアント側プラグインとして追加する。
  - クライアントは利用可能なモーション・表情のプリセットを`ClientCapabilitySpec.presets`に含め、`input_schema`とともにホストへ公開する。ホストはそれをモデル向けツールの説明に反映するが、再生処理は持たない。
  - 「頭」が`body_motion`を呼ぶと、ホストは`DeviceOperation { capability: "body.motion", input: ... }`を送出する。モーション名・表情名の解釈と再生はクライアント側プラグインが行う。
- **デスクトップギミック（クライアント側）**:
  - 画面の端に座る、アクティブウィンドウの上に乗る、ウィンドウの移動に合わせて跳ねるといったデスクトップ連携ギミックは、クライアント側プラグインの責務である。
  - クライアントは`body.window_perch`のような能力を`ClientCapabilitySpec`で宣言し、ホストは`device_request`または動的に登録されたツールから同じ`DeviceOperation`経路で呼び出す。ホストはウィンドウ追従や描画の実装詳細を知らない。
  - ファイル・画面操作などの高リスク能力は`approval = CONFIRM`とし、能力の許可だけで素通しせず、操作ごとに`Stage::Gate`と`ApprovalRequest`を通す。
  - デスクトップクライアントでの具体的な実装は[デスクトップクライアント設計](desktop-client.md)を参照する。

## 3. ライフサイクルフック（Lifecycle Hooks）とセキュリティ境界

プラグインがホスト内の処理に関与する場合、セキュリティ境界と承認の整合性を維持するため、フックの実行権限と変更可能性（Mutability）を厳格に制限する。

```text
                  [ユーザー入力 / 音声STT]
                             │
                             ▼
                    ┌─────────────────┐
                    │  on_perception  │ ── 知覚メタデータのマスキング（認可前・サニタイズ）
                    └────────┬────────┘
                             │
                             ▼ (判定パイプライン & ユーザー承認)
                             │
                    ┌──────────────────┐
                    │ before_tool_exec │ ── 実行前監査ログ（読み取り専用・引数改ざん禁止）
                    └────────┬─────────┘
                             ▼
                    [ツール / サンドボックス実行]
                             │
                             ▼
                    ┌──────────────────┐
                    │ after_tool_exec  │ ── 実行結果の観察ログ（成否の書き換え禁止）
                    └────────┬─────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  before_speak   │ ── 発話テキストの演出タグ付与（表示・音声加工）
                    └────────┬────────┘
                             ▼
                    [発話出力（TTS・音声）]
                             │
                             ▼
                    ┌─────────────────┐
                    │   after_speak   │ ── 発話完了の観察通知（読み取り専用）
                    └─────────────────┘
```

### フックの種別と制約

| フック名 | 性質 | 発火タイミング | 制約・保証 |
| :--- | :--- | :--- | :--- |
| **`on_perception`** | 加工可 | 知覚データ受信直後 | プライベート情報のマスキングや不要メタデータの除外。親の推論前に実行 |
| **`before_tool_exec`** | **読み取り専用** | ツール実行直前 | **承認済み引数の書き換えは固く禁止**。ホスト内部の監査ログ記録のみ許可（無認可の外部送信はWasm/Sandbox境界で遮断） |
| **`after_tool_exec`** | **読み取り専用** | ツール実行直後 | **失敗結果を成功へ改ざんすることは禁止**。実行実績の通知・ログ記録のみ許可 |
| **`before_speak`** | 加工可 | 音声合成直前 | 口調の微調整や演出タグの挿入。記憶の正本ログ本文は改変しない |
| **`after_speak`** | **読み取り専用** | クライアント再生完了後 | 会話統計の収集や外部連携。失敗しても対話セッションを中断しない |

> [!IMPORTANT]
> **認可とInterceptorの順序規則**:
> ユーザーが承認した操作の引数を、プラグインが `before_tool_exec` で事後的に書き換えることはセキュリティ上遮断される。引数が変更された場合、[権限設計](permissions.md) に基づきハッシュ不一致として承認は即座に失効する。
> Alpha初期においては、ツールの提供（MCP/Wasm）、知覚センサー、およびモーションの3大拡張を主軸とし、内部処理を書き換える可変フックは必要最小限に留める。

## 4. コーディング特化・タスク別プロファイル切替の非採用

コーディングエージェント製品（Roo Code / Cline等）では、「Architect」「Code」「Ask」「Test」のようにエージェントのモードやプロファイルを切り替える設計が一般的である。
しかし、eneでは **このようなタスク特化プロファイルの切り替えを明確に採用しない**。

### 非採用の理由
1. **キャラクター同一性の破壊**:
   - eneは「ユーザーと共に生きるデスクトップAIコンパニオン」である。作業モードを切り替えるたびにキャラクターの人格、口調、対人姿勢がリセットされたり、無機質なコーディングマシンに変貌することは、コンパニオンとしての愛着と信頼関係を根底から損なう。
2. **「頭」と「手」の直交性**:
   - 作業の専門性や重い実装は、すべて「手」（Hands / WorkSession）に自然言語で委託される。「手」は外部ハーネス（ACP）やMCPを通じて最高峰のエンジニアリング能力を発揮できるため、親である「頭」自身の人格プロファイルを改変する必要がそもそも存在しない。
3. **ユーザー体験の分断防止**:
   - ユーザーは「今はコーディングモードだからあの指示を出そう」とシステム都合のモードを意識する必要がなく、常にいつものパートナーとして自然に作業を相談・依頼できる。

## 5. プラグインの配布・検証・セキュリティ

プラグインの形態に応じた多層セキュリティ境界を定義する：

1. **内部Bevyプラグイン（In-Process）**:
   - ホストと同一バイナリ・同一メモリで動作する信頼済みコード。
2. **Wasmプラグイン（Extism組み込み）**:
   - 配布パッケージ内の Extism Manifest に基づき、厳格なリソース・ネットワーク制限を適用する：
     - `allowed_hosts`: 外部通信を許可する特定のFQDN/ドメインのホワイトリスト（未指定時はネットワーク遮断）。
     - `allowed_paths`: マウントを許可するローカルパスのホワイトリスト（パストラバーサル防止）。
     - `memory.max_pages`: 最大メモリ使用量制限。
     - `timeout_ms`: 実行タイムアウト制限。
   - Manifest で明示的に許可されていない通信やファイルアクセスは、Extism/Wasm ランタイムにより決定論的に遮断される。
3. **外部ACPタスクハーネス**:
   - [権限設計](permissions.md) に基づき、OSネイティブSandbox（Linux Landlock/bwrap、Windows AppContainer）によってプロセスレベルで隔離される。
4. **プライバシーデータの漏洩防止**:
   - ユーザーの個人的な記憶やプライベートな会話ログ全文をプラグインへ無条件に流すことはせず、プラグインが要求したCapabilityおよびユーザーが許可したコンテキスト（知覚要約など）に限定して受け渡す。
5. **クライアント側プラグイン（ホストSandbox外）**:
   - クライアント内で動作する知覚・表現プラグインは、ホストのプロセスSandboxやWasm境界の外にあり、クライアントの権限とOSの許可に従う。
   - ホストは`ClientCapabilitySpec`の入力スキーマ検証、能力の許可判定、`Stage::Gate`と必要な`ApprovalRequest`、`DeviceOperation`の配送を行い、クライアントのローカル実装や取得した知覚情報の完全性を信頼しない。
   - クライアント側プラグインが取得した情報は、ホストが検証可能な事実（タイトル、アプリID、明示的な要約）として受け取り、推測と混同しない。
