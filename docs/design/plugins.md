# プラグイン・拡張アーキテクチャ（Everything is a plugin）

状態：Alphaの採用設計（2026-11-11策定）。[全体アーキテクチャ](../architecture.md)、[機能の拡張](../features/extensions/README.md)、[作業相手API](work.md)、[知覚・自律ループ・音声](loop-perception-voice.md)、[権限](permissions.md)を参照する。

## 1. 設計思想：Everything is a plugin

eneにおける拡張性は、単なる「外部APIツールの追加」にとどまらない。デスクトップ常駐AIコンパニオンとしての全方位の能力をプラグインとして拡張・差し替え可能にする **"Everything is a plugin"** を設計原則とする。

システムを「頭」「手」「目」「体」の4つの境界に整理し、このうち **「手」「目」「体」の3つを主要なプラグイン拡張ポイント** として開放する。

| 拡張ポイント | 役割 | プラグインの形態 |
| :--- | :--- | :--- |
| **「手」の拡張（Actions & Tools）** | 実務タスク遂行、外部操作 | MCP（Model Context Protocol）サーバー、Wasmプラグイン（Extism）、ACP外部タスクハーネス |
| **「目」の拡張（Perception Sensors）** | 環境知覚、状況認識 | IDE連携センサー、ブラウザ監視拡張、OSイベントフック、アクティブウィンドウWatcher |
| **「体」の拡張（Body & Expressions）** | 身体表現、デスクトップ演出 | VRMAアニメーション、ブレンドシェイプ表情プリセット、デスクトップギミック（座る、窓押し等） |

---

## 2. 三大拡張ポイントの技術仕様

### 1. 「手」の拡張（Actions & Tools）
作業エージェント（Hands / WorkSession）が実務タスクで使用するツールや実行基盤の拡張。
- **MCP（Model Context Protocol）接続**:
  - 業界標準のMCPプロトコルに基づき、ローカルまたはリモートのMCPサーバーを登録。
  - ホストがMCPクライアントとして接続し、利用可能なツール一覧を「手」へ提供する。
- **Wasmプラグイン（Extism組み込み）**:
  - 安全にサンドボックス化されたWebAssemblyプラグイン。ファイル操作やネットワーク通信はホストが認可したCapabilityの範囲に厳格に制限される。
- **ACP（Agent Client Protocol）外部ハーネス**:
  - 特化型のエージェント実行環境（例: 高機能コーディングハーネス）をACP経由で接続し、一連のタスク実行をまるごと委託可能。

### 2. 「目」の拡張（Perception Sensors）
デスクトップの状況やユーザーの作業状態をセンシングする知覚の拡張。
- **センサープラグインの責務**:
  - OSや各種アプリケーション（VS Code、Chrome、端末エミュレータ等）からのイベントを購読、または定期サンプリングを行い、生のイベントデータをホストへ送信する。
  - ホストはこれを受信し、簡潔な知覚要約（Perception Summary）に変換して「頭」の動的文脈枠へ注入する。
- **動的Watcher対応**:
  - 「頭」が `set_eye_watch` で指定した監視条件をセンサープラグインがリアルタイム評価し、合致時に優先割り込み通知（Priority Interrupt）をホストへ返す。

### 3. 「体」の拡張（Body & Expressions）
デスクトップ上のアバター表現や演出の拡張。
- **VRMAモーション・表情パッケージ**:
  - 新たな待機モーション（Idle）、相槌モーション（Nod）、喜び・驚きなどの感情アクション、身振り手振りをプラグインとして追加。
  - 「頭」が出力する `body_motion` ツール引数でモーション名や表情名を指定することで即時再生される。
- **デスクトップギミック**:
  - 画面の端に座る、アクティブウィンドウの上に乗る、ウィンドウの移動に合わせて跳ねるといったデスクトップ連携ギミック。クライアント描画プロセス（`ene-avatar`）と連携して描画される。

## 3. ライフサイクルフック（Lifecycle Hooks）

プラグインは単なるツールの提供だけでなく、ホスト内の主要なライフサイクルイベントをフックし、挙動の観察や入力・出力の変換（Interceptor）を行うことができる。

```text
                  [ユーザー入力 / 音声STT]
                             │
                             ▼
                    ┌─────────────────┐
                    │  on_perception  │ ── 知覚データの整形・コンテキスト付与
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │  before_speak   │ ── 発話テキストのサニタイズ・演出タグ付与
                    └────────┬────────┘
                             ▼
                    [発話出力（TTS・音声）]
                             │
                             ▼
                    ┌─────────────────┐
                    │   after_speak   │ ── 発話ログの監査・感情分析・外部連携
                    └────────┬────────┘
                             │
      (タスク委託時)          │
                             ▼
                    ┌──────────────────┐
                    │ before_tool_exec │ ── ツール実行前の引数検証・監査ログ
                    └────────┬─────────┘
                             ▼
                    [ツール / サンドボックス実行]
                             │
                             ▼
                    ┌──────────────────┐
                    │ after_tool_exec  │ ── 実行結果の成形・エラーハンドリング
                    └────────┬─────────┘
                             │
      (アイドル時)            │
                             ▼
             ┌───────────────────────────┐
             │ on_memory_consolidation   │ ── 記憶整理時のカスタム索引付け・外部出力
             └───────────────────────────┘
```

| フック名 | 発火契機 | 主な用途 |
| :--- | :--- | :--- |
| **`on_perception`** | 「目」からの知覚イベント検知時 | 知覚メタデータの補正、プライベート情報のマスキング、追加コンテキストの付与 |
| **`before_speak`** | 「頭」が `talk` を生成し発話する直前 | 口調の微調整、テキストのサニタイズ、特殊音声演出タグの挿入 |
| **`after_speak`** | 発話がクライアント側で完了した直後 | 発話ログの外部記録、会話統計の集計、感情ログの追跡 |
| **`before_tool_exec`** | 「手」がツールやコマンドを実行する直前 | ツール引数の追加検証、レートリミット、実行前監査ログの記録 |
| **`after_tool_exec`** | ツール実行が完了した直後 | ツール実行結果のフィルタリング、成功/失敗の外部通知 |
| **`on_memory_consolidation`** | アイドル時の記憶自動整理完了時 | 外部ナレッジベースへの記憶同期、独自フォーマットでの長期バックアップ |

## 4. コーディング特化・タスク別プロファイル切替の非採用

コーディングエージェント製品（Roo Code / Cline等）では、「Architect」「Code」「Ask」「Test」のようにエージェントのモードやプロファイルを切り替える設計が一般的である。
しかし、eneでは **このようなタスク特化プロファイルの切り替えを明確に採用しない**。

### 非採用の理由
1. **キャラクター同一性の破壊**:
   - eneは「ユーザーと共に生きるデスクトップAIコンパニオン」である。作業モードを切り替えるたびにキャラクターの人格、口調、対人姿勢がリセットされたり、無機質なコーディングマシンに変貌することは、コンパニオンとしての愛着と信頼関係を根底から損なう。
2. **「頭」と「手」の直交性**:
   - 作業の専門性や重い実装は、すべて「手」（Hands / WorkSession）に自然言語で委託される。「手」は外部ハーネス（ACP）やMCPを通じて最高峰のエンジニアリング能力を発揮できるため、親である「頭」自身の人格プロファイルを改変する必要がそもそも存在しない。
3. **ユーザー体験の分断防止**:
   - ユーザーは「今はコーディングモードだからあの指示を出そう」とシステム都合のモードを意識する必要がなく、常にいつものパートナーとして自然に作業を相談・依頼できる。

## 5. プラグインの配布・検証・セキュリティ

- プラグインの配布パッケージには、マニフェスト（Capability要求、提供ツール一覧、知覚センサー種別、モーションデータ定義）を含める。
- プラグインが要求するアクセス権限は、[権限の設計](permissions.md) に基づき、Sandbox境界および自動判定エンジン（Decision Engine）によって厳格に制御される。
- ユーザーの個人的な記憶やプライベートな会話ログを、プラグイン作者や外部サービスが無断で取得・流出させることはアーキテクチャレベルで遮断される。
