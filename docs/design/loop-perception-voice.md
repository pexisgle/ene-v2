# 知覚・自律ループ・音声・アバター連携設計

状態：Alphaの採用設計（2026-11-11策定）。[アーキテクチャ](../architecture.md)、[心と自動記憶](mind.md)、[作業相手API](work.md)、[自発的見守り機能](../features/autonomy/watch-over.md)、[音声機能](../features/voice/README.md)を参照する。

## 1. 目的と全体像

デスクトップコンパニオンとして、ユーザーの作業や日常をリアルタイムに見守り、遅延なく自然に会話・リアクションを行うための統合ループアーキテクチャを定義する。

```text
                     ┌──────────────────┐
                     │ ユーザー・PC環境 │
                     └────┬────────▲────┘
       OSイベント / 画面知覚 │        │ 音声発話 / 画面カード
                          ▼        │
  ┌────────────────────────────────────────────────────────┐
  │ 「目」（知覚 / Perception）                             │
  │  ・イベント駆動 + アイドルサンプリング（15〜30秒）       │
  │  ・高解像度知覚要約の生成                               │
  │  ・動的Watcher条件による能動的割り込み検知               │
  └───────────────────────┬────────────────────────────────┘
                          ▼ 知覚イベント / 割り込み
  ┌────────────────────────────────────────────────────────┐
  │ 「頭」（Brain / 親エージェント）                        │
  │  ・行動選択ループ（Rig推論）                             │
  │  ・ツール呼出: talk / body_motion / instruct_hand      │
  │              / set_eye_watch / noop                    │
  └───────┬───────────────────────────┬────────────────────┘
          │ instruct_hand             │ talk / body_motion
          ▼                           ▼
  ┌───────────────┐           ┌────────────────────────────┐
  │ 「手」（Hands）│           │ 音声・アバター描画（Body）  │
  │  実務タスク    │           │  ・Adaptive Barge-in       │
  │  バックエンド │           │  ・クライアント即時リップ   │
  └───────────────┘           │  ・リアルタイムモーション  │
                              └────────────────────────────┘
```

## 2. 「目」（知覚 / Perception）のハイブリッド収集

デスクトップ上の状況変化を無駄なリソース消費なく、かつ取りこぼしなく捉えるため、イベント駆動とサンプリングを組み合わせたハイブリッド方式を採る。

### イベント駆動 ＋ アイドルサンプリング
1. **イベント駆動（即時検知）**:
   - アクティブウィンドウのフォーカス切替、作業ファイルの保存・変更、ブラウザのURL遷移、プロセスの起動・終了などのOSイベントをフックして即座に捉える。
2. **アイドルサンプリング（定期補完）**:
   - 数十秒間イベントが発生しない静止状態であっても、**15〜30秒間隔**で現在の画面状態（フォアグラウンドアプリ、ウィンドウタイトル等）をサンプリングし、見守りの連続性を維持する。

### 高解像度知覚とセマンティック要約
- 取得したOSの生情報（例: ウィンドウハンドル、プロセス名、フルパス、画面解像度）をそのままLLMに流し込むのではなく、**「ユーザーが今何をしているか」の簡潔な意味論的要約（Perception Summary）**にホスト側で整形する。
  - *例*: `VS Codeで ene-v2/docs/design/mind.md を編集中（直前のビルド: 成功）`
- この知覚要約を、親（頭）のプロンプトの動的文脈（Dynamic Context）枠へ毎ターン最新状態で注入する。

### 動的Watcher（能動的監視と割り込み）
- 親（頭）は、対話やタスクの文脈に応じて「特定のことに関してすぐ通知してほしい」という条件を「目」に動的登録できる。
  - ツール呼出: `set_eye_watch(condition: String, notify_immediately: bool)`
  - *例*: `set_eye_watch(condition: "cargo build またはテストが完了したとき", notify_immediately: true)`
- **即時通知**: 登録されたWatcher条件に合致する事象が発生した場合、定期サンプリング間隔を待たずに**即時優先イベント（Priority Interrupt）**として親（頭）へ送信され、親が即座にリアクションを発話できるようにする。

## 3. 「頭」（Brain / コンパニオンAgent）のアクションループ

ユーザーからの入力（音声・テキスト）、作業「手」からの報告、または「目」からの知覚変化を受け取った親（頭）は、Rigの実行カーネルを通じて次の行動を自律選択する。

### LLMが出力するアクションツール群
親（頭）は、以下の軽量ツール呼び出し（Tool Call）を通じて行動を決定する。

| ツール | 引数 | 役割 |
| :--- | :--- | :--- |
| **`talk`** | `utterance: String`<br>`cited_memories: Vec<String>`<br>`motion_intent: Option<String>` | ユーザーへの発話（音声合成およびテキスト表示）。参照した記憶IDの明示、および発話時の身振り意図 |
| **`body_motion`** | `motion_name: String`<br>`expression: String`<br>`duration_ms: u32` | アバターのVRMAモーション・表情のリアルタイム直接制御（発話時以外の単独実行が可能） |
| **`instruct_hand`** | `instruction: String` | 「手」（Hands / WorkSession）に対する実務タスクの自然言語委託 |
| **`set_eye_watch`** | `condition: String`<br>`notify_immediately: bool` | 「目」（知覚センサー）に対する動的監視条件の登録 |
| **`noop`** | *なし* | 何も行わない（環境変化を見守るのみ、または他者宛て発話を受け流す） |

### リアルタイムモーションの直接制御
- アバターのモーション・表情制御は、発話（`talk`）の付属物にとどまらない。
- 親（頭）は、**話すとき以外であっても `body_motion` をいつでも単独で呼び出すことができる**。
  - ユーザーが話している最中に相槌として「頷く（nod）」
  - 画面の作業を眺めて「首を傾げる（tilt_head）」
  - アイドル時に「伸びをする（stretch）」
  - 「手」の作業完了通知を受けて「喜ぶ（joy_expression）」
- これにより、発話していない時間も含めて生きたキャラクターとしての存在感を維持する。

## 4. 音声パイプラインと全二重（Full-Duplex）対話（参考：Shizuku-Duplex方式）

> [!NOTE]
> Shizuku-Duplex の設計思想（常時傾聴、ひとりごとステートマシン、文節ストリーミング、適応型バージイン等）は、**低遅延対話の参考モデル（リファレンス）**であり、すべての機構を一律に強制するものではない。
> 実際の音声パイプラインは、採用するTTS/STTエンジン（VOICEVOX等の文単位HTTP API、sherpa-onnx等のストリーミングエンジン、OpenAI Realtime等の双方向Live API）の通信仕様や機能特性に合わせて柔軟に実装・適応する。

従来の直列カスケード型対話（「ユーザーが話し終わり、一定時間の無音を待ってから ASR ➔ LLM ➔ TTS を順次実行する」ターン制）では、応答までに数秒の気まずい沈黙（レイテンシ）が生じ、発話中の自然な相槌や割り込みも困難であった。
eneでは、エンジンの仕様に合わせて先行合成や割り込み破棄を適切に行うことで、人間らしく滑らかな音声対話を実現する。

```text
                             ┌── (ストリーミングSTT中間結果) ──┐
                             ▼                                │
[ユーザー発話] ──→ [音声ストリーミング入力]                   │
                             │                                ▼
                             │                 [ひとりごと / Inner Monologue]
                             │                 ・相手は話し終えたか？
                             │                 ・相槌（うん、へえ）を入れるか？
                             │                 ・本格的に話し始めるか？
                             │                 ・静かに聞くべきか（沈黙）？
                             ▼                                │
                     [発話終了 / 句切り検知]                  ▼
                             │                 [文節単位ストリーミングTTS]
                             └─────────────────→ 「〜だね、」（即座に初声再生）
                                                 「それで〜」（並行して先行合成）
```

### 1. ストリーミング全二重音声処理（Full-Duplex Processing）
- **常時リスニング**: コンパニオン自身が話している最中や思考中であっても、マイク入力は小チャンク単位でリアルタイムにストリーミング取得・認識される。
- **ターン交代待ちの排除**: 「発話終了の長い沈黙（例: 800ms〜1.5秒）」を待ってから初めて動き出すのではなく、ストリーミングSTTの中間テキストや音響韻律（ピッチ下降や息継ぎ）から相手の話の終わりや間合いを先行予測する。

### 2. 「ひとりごと（Inner Monologue）」による自律的ターンテイキング
Shizuku-Duplex の中核である「ひとりごと」プロセスを取り入れ、音声をいきなり合成・出力する前に、内部で軽量な意思決定（思考ステップ）を挟む。
- **リアルタイムな振る舞い判定**:
  - **即時相槌（Backchannel）**: 相手の話がまだ続いている場合、話を遮らずに「うん」「なるほど」「うんうん」といった短い相槌音声を適切な間合いで返す。
  - **発話開始（Start Speaking）**: 相手が一区切り話し終えた、または質問されたタイミングで即座に本格的な返答を開始する。
  - **沈黙維持（Keep Listening）**: まだ相手が言葉を選んでいる（間を置いている）と判断した場合は、無理に口を挟まず静かに待つ。

### 3. 文節単位のストリーミングTTSと初声遅延（TTFA）の最小化
- **先行パイプライン合成**: LLMからの応答テキストを全文完成まで待たず、句読点や文節（「〜だよ、」「それでね、」）単位で順次TTSストリーミングエンジンへ投入する。
- **Time-to-First-Audio（TTFA）の極小化**: 最初の文節が生成された瞬間に音声再生を開始し、再生中に後続の文節を並行合成することで、初声までの遅延を数百ミリ秒〜1秒未満に抑え、人間同士のようなテンポ良い掛け合いを実現する。

### 4. 2層構造の協調（Interaction Model と Background Model）
Shizuku-Duplex の2層アーキテクチャに倣い、「頭」と「手」の協調を音声対話のリズム維持に直結させる。
- **「頭」（Interaction Model）**: ユーザーとの即時会話、相槌、短い応答、アバターのリアルタイムモーション制御を担当し、会話のテンポを絶対に止めない。
- **「手」（Background Model / WorkSession）**: Web検索やファイル操作、コーディングなどの重い実務を非同期バックグラウンドで実行。
- 「手」が裏で作業している最中も、「頭」は「今調べてるよ」「ちょっと待ってね」といった繋ぎの発話や相槌を自然に返し、不自然な無音フリーズを発生させない。

### 5. 適応型バージイン（Adaptive Barge-in）
コンパニオンが発話している最中にユーザーが声を被せてきた場合の衝突（Barge-in）を音響特性に応じて賢く制御する。
- **微小な相槌・環境音（< 0.3秒）の無視**:
  - ユーザーの短い相槌（「うん」「へえ」）、咳払い、タイピング打鍵音などは、発話を中断させずにそのまま喋り続ける。
- **実質的な割り込み（>= 0.5秒）の即時中断**:
  - ユーザーが実質的な言葉を話し始めた場合、コンパニオンは即座に発話生成を中断する。
  - クライアント側（表示・音声再生部）へ直ちに `interrupt` シグナルを送り、**再生中の音声バッファを即座に破棄（Flush）**して静寂を確保し、ユーザーの発話傾聴へ移行する。

### 6. リアルタイムLive API方式の選択肢
- 上記のSTT/TTSストリーミングパイプラインに加え、OpenAI GPT-4o Realtime API や Gemini Live API 等への直接ストリーミング接続も利用可能とし、環境やモデル提供状況に応じた最適な低遅延体験を提供する。

## 5. アバター描画・リップシンク（Body連携）

VRMアバターの描画と同期制御はクライアントプロセス（`ene-avatar` / Bevy App）が担当し、ネットワーク往復の遅延を排した即時同期を実現する。

### クライアント側RMS音量によるゼロ遅延リップシンク
- サーバー側でリップシンク用の音素（Viseme）解析を同期生成して送信するのではなく、**クライアントが受信した音声ストリームのRMS（実効値）音量をローカルでリアルタイム解析**する。
- 音量振幅に応じてVRMの口形状ブレンドシェイプ（`aa` 等）を直接変位させることで、ネットワーク遅延やパケットゆらぎに影響されない完全な口パク同期をゼロコストで実現する。

### モーションと表情の合成
- `body_motion` で指示されたVRMAアニメーションと表情ブレンドシェイプは、クライアント内のBevy ECS上で現在の待機ポーズ（Idle）や視線追従（LookAt）とスムーズにクロスフェード合成される。

## 6. 複数コンパニオンの調停（Multi-Companion Arbitration）

複数体のコンパニオン（GrokBot方式）がデスクトップ上に同時に常駐している場合の対話調停ルール。

```text
[ユーザーの音声発話] ──→ [STT音声認識]
                               │
               ┌───────────────┴───────────────┐
               ▼ (名前フィルタせず同報配信)      ▼
       [コンパニオン A]                 [コンパニオン B]
         自律判断                         自律判断
      「私宛ての発話だ！」             「私宛てではないな」
               │                                │
               ▼                                ▼
       talk("了解だよ！")                     noop()
               │
               ▼ 先着優先でフロア獲得
       [音声再生開始]
               │
               ▼ 発話終了
       [speech_completed 通知] ──────────→ 「Aが話し終わったから補足しよう」
                                                │
                                                ▼
                                         talk("私も手伝うね")
```

### STTの全員同報配信（フィルタリングの排除）
- クライアント側で正規表現や名前による「誰宛てか」の振り分け・フィルタリングは行わない。
- 認識されたテキストは、稼働中の**すべてのコンパニオンの「頭」へ等しく同報配信（Broadcast）**される。

### 自律的な該当性判断（Self-Relevance）
- 各コンパニオンの「頭」は、自身のプロンプト・人格・文脈に照らし、「この発言は自分に向けられたものか」を各自で自律的に判断する。
- 他のコンパニオン宛ての発言、または自分に関係のない話題であると判断した場合、そのコンパニオンは `noop()` を返し、発話権を主張しない。

### フロア制御（先着優先）
- 複数のコンパニオンが同時に自分宛てと判断して発話を返そうとした場合、ホスト側で**最初に `talk` ツールを確定させたコンパニオンが発話権（Floor）を獲得**する。
- 競合した2体目以降の発話は、音響的な重複を避けるために一旦キューイングまたは保留される。

### 完了トリガー（Turn-taking）による自然な掛け合い
- 発話権を得たコンパニオンの発話が完了すると、ホストから他のコンパニオンへ **`speech_completed` イベント** が配信される。
- これを受け取った他のコンパニオンは、「相手の発言を受けて相槌を打つか」「話題を補足するか」を再評価でき、複数コンパニオン間での自然で生き生きとした掛け合い・会話リレーを実現する。
