# ホスト API の概要

この文書では [用語集](terms.md) と [全体アーキテクチャ](architecture.md) を前提に、ホストとクライアントを結ぶ通信基盤の基本方針・6 つのサービス領域の分担・受付と状態同期および停止制御の境界をまとめます。
実装やプロトコルの発展に合わせて柔軟に変更する余地を保つため、個別の要求名やメッセージ型の具体的な定義は [host.proto](../crates/ene-rpc/proto/host.proto) へ譲る構成です。
接続の認証と操作の確認制御は [作業実行・操作確認・接続保護の設計](design/work.md)、端末連携や音声・知覚は [クライアント設計](design/client.md)、心・記憶・拡張は [心・記憶・会話圧縮の設計](design/mind.md) と [プラグイン拡張の設計](design/plugins.md) を参照してください。

## 通信基盤とサービス領域の分担

常駐ホストとクライアントは型付きの通信契約とストリーミングを備える `Connect-RPC` での接続を基本としつつ、ブラウザなどの双方向ストリームを扱いにくい環境向けには代替の転送経路も選択できる余地を残します。

| サービス領域 | 主に担う操作とやり取り |
| --- | --- |
| ホスト状態・心・記憶 | 全体状態のスナップショット取得、通知購読、コンパニオンや心・記憶の参照と調整 |
| 会話 | 発言の受付、生成の停止、会話履歴の取得 |
| 設定・承認・プラグイン | 接続設定やモデル一覧の管理、安全確認用の規則と自由文ポリシー・承認回答、プラグインの着脱 |
| 作業 | 作業セッションの一覧・状態確認、直接指示や緊急停止などの制御 |
| 音声 | 音声入力の送信、合成音声の受信、発話指示 |
| クライアント | 端末登録、アクティブ端末の切り替え、知覚報告や端末操作の配送と完了通知 |

クライアント側へ会話や作業の判断・取りまとめを担う「頭」の進行制御を持ち込まない原則とし、日常の作業依頼・追加指示・記憶の訂正や忘却はいずれも対話経路を通じてコンパニオン本人へ届け、開発支援や緊急停止に用いる直接操作とは明確に分けて扱う設計です。

## 受付・冪等性・エラー表現の方針

対話応答や作業のように完了まで時間を要する要求では受付と処理完了を明確に分け、受付時には追跡用の識別子だけを返して途中の経過や最終結果を通知と状態取得から確認します。
状態を変更する要求には要求キーを持たせ、同じキーかつ同じ内容の再送には元の受付結果を返して二重実行を防ぐ規則です。
同じキーで異なる内容の再送や対象の状態が先に進んでいた場合の更新は競合として拒否し、API キーなどの資格情報を再送比較用の記録へは残しません。
さらに通信契約やホスト側処理で未知の状態・破損した応答・不明な終了理由を受けた場合は正常完了へ丸め込まず、未対応・権限不足・競合・通信障害・保存失敗・成否不明を区別して返し、エラー詳細にも資格情報や非公開の `記憶` を含めません。

## 状態購読・再接続と停止の扱い

状態の基準はホスト側に保存されたデータへ置き、初期状態のスナップショット取得と連続的なイベント購読を組み合わせることで、遅延や通信断で通知を取りこぼしても再同期や再取得により最新状態へ復帰できる構成とします。
生成途中に少しずつ届く文字片や作業の経過通知と保存済みの確定本文・終了状態は分けて扱い、遅延して届いた古い更新通知によってクライアント側の最新表示を巻き戻さない原則です。
クライアントの一時的な通信切断は処理の停止要求とはみなさず、会話生成の停止・特定作業の停止・ホスト自体の終了を明確に分けたうえで、UI からの明示的な停止操作はモデルの応答を待たない直接の制御経路で受け付けます。

## クライアント能力・音声・アクティブ端末の境界

クライアントは接続時に自身が持つ `端末能力` を申告する立場にとどまり、能力の許可判断と確認制御は常にホスト側が握って承認境界を通した操作だけをアクティブなクライアントへ配送するため、クライアントが自らへ権限を付与することは許さない構成です。
音声の入出力や知覚の報告は各クライアントの接続およびアクティブ状態へ結び付け、利用中のアクティブ端末を切り替えた際は旧端末での音声再生と音声出力の占有を止め、ホスト側で旧端末に結び付いていた発話の再生状態も解放して、旧端末から遅れて届く入力を破棄します。
一方でアクティブ端末の切り替えと単なる一時切断は明確に区別し、一時的な通信断だけで進行中の作業や端末操作を直ちに失敗扱いへせず、再接続と状態再取得を待って安全に引き継ぐ方針です。
