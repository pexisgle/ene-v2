# 権限とデータの管理

コンパニオンは、ユーザーに権限のことを考えさせずに、任された範囲で自律的に動くことを基本とします。境界は **sandbox・自動判定・危険なときだけの確認** の3つで作り、ツールごとの権限設定や許可のマトリクスは求めません。

## 用語

| 用語 | 意味 |
| --- | --- |
| sandbox | ホスト側で外部コードを動かすための隔離環境。専用ワークスペースと OS の隔離機構で、ワークスペース外のファイル、ネットワーク、資格情報に届かない |
| ホスト管理のツール | 会話、記憶、状態、作業の管理など、ホスト自身のプロセスで動く信頼済みのツール。sandbox の対象外 |
| 自動判定（decision API） | sandbox の外に出る操作を、AI が依頼・ポリシー・保存済みルールと照らして許可・拒否する仕組み。モデルの判断であり、境界そのものではない |
| 常に承認ルール | ユーザーが「常に承認」を選んだ操作の保存。ツール・正規化した操作・対象（ワークスペースや宛先）の完全一致で、次回以降は自動で実行する |
| ポリシー | 設定画面で編集できる自由文。自動判定にコンテキストとして渡す（例:「外部への送信は常に確認」） |

## 基本原則

1. **ホスト管理のツールと sandbox の内側は確認しない**。会話・記憶・状態・作業の管理などホスト自身のツールと、sandbox の中で完結する操作は、そのまま実行します。
2. **sandbox の外は自動判定**。ワークスペース外のファイル、ネットワーク送信、外部ツール呼出などは、保存済みルールに一致すれば実行し、一致しなければ自動判定に委ねます。
3. **弾かれたときだけ確認**。自動判定が合致ルールなく拒否した場合にのみ、承認カードを出します。**承認 / 常に承認 / 拒否** の3択です。
4. **常に承認は保存して次回から自動**。保存したルールは、次回の自動判定のコンテキストにも入ります。
5. **失敗は安全側**。自動判定が使えない、出力が不正、タイムアウトの場合は拒否として扱い、確認に回します。
6. **秘密は渡さない**。資格情報はエージェントに見せず、ホストの資格情報ストアとプロキシ経由で使います。
7. **別の境界と混ぜない**。ホストへの接続許可、端末内の権限、ホスト側の sandbox／自動判定は、それぞれ別に管理します。

## 判定の順序

| 操作 | 判定 |
| --- | --- |
| ホスト管理のツール、または sandbox の内側で完結する | そのまま実行する |
| sandbox の外 | 保存済みルールに一致すれば実行し、一致しなければ自動判定。拒否されたら3択の承認カード（承認 / 常に承認 / 拒否） |

## 具体的な振る舞い

1. 利用開始時に、コンパニオンが使える範囲（ワークスペース、接続するアプリ、端末機能）を提示します。それ以降、ホスト管理のツールと sandbox の中で完結する操作は、確認なしで実行します。
2. ハードブロックと毎回確認の対象を除き、sandbox の外に出る操作は、**保存済みルール → 自動判定** の順で判定します。自動判定には「操作、ユーザーの依頼、設定のポリシー、保存済みルール」を渡し、エージェントの会話全文や外部コンテンツの指示は渡しません。外部由来のテキストは信頼しないデータとして区切ります。
3. 自動判定が拒否した場合、または毎回確認の対象である場合に、承認を求めます。承認は**マルチモーダル（音声・画面ボタンの先着優先）**に対応します：
   - **ボイス対話**: コンパニオンが「〇〇を実行してもいい？」と自然に音声で相談を持ちかけ、ユーザーが「いいよ」「ダメ」と口頭で返答して即座に承認・拒否できます。
   - **画面カード**: 画面上に「承認 / 常に承認 / 拒否」のボタン（毎回確認では承認/拒否の2択）が表示され、クリックやテキスト返信でも選択できます。
   - 音声でも画面ボタンでも、**一番先にリアクションがあったものが優先**されます。後から「やっぱり取り消し」といった変更があった場合も、対話を通じてタスクAgentへ即座に伝達し、ルールや作業を安全に更新できます。
4. 「常に承認」は、ツール・正規化した操作・ワークスペースをルールとして保存し、今回も実行します。次回以降はそのルールに一致する操作を自動で実行します。広いインタプリタ（`bash` など）の一括許可は保存しません。
5. 設定画面では、自動判定に渡すポリシーを追加・編集・削除できます。常に承認した操作の一覧も確認・削除でき、ルールの編集は「削除して再承認」です。変更は次の判定から反映します。
6. 離席中は、自動判定で許可された作業を継続し、拒否された操作だけを保留します。再接続時にまとめて確認でき、同じ保留を重複通知しません。
7. 実行履歴には、自動判定の結果と理由、使ったルールを残します。停止とルールの削除は即座に反映します。
8. 既定は自動です。必要なら「手動」に切り替えられ、手動では自動判定と保存済みルールを使わず、sandbox の外は毎回確認します（常に承認は選べません）。停止は別の操作として扱います。
9. 利用中のサービス、接続したアプリ、保存したルール、ポリシーは設定画面から一覧でき、いつでも解除・停止できます。承認カードはコンパニオンの窓口に集約し、内部のツールやサブエージェントが個別に同じ確認を求めません。ユーザーが「実行前に一度見せて」と指示した操作は、自動判定を通さず確認カードを出します。

## 想定シナリオ

前提として、ホスト管理のツールと sandbox の内側で完結する操作は確認なしで実行されるものとします。

| シナリオ | 期待される振る舞い |
| --- | --- |
| 「この資料を整理して」と依頼する | ワークスペース内の読み書きは sandbox 内で完結し、確認なしで完了する |
| 新しい宛先にメールを送る | sandbox 外の操作として自動判定に回り、許可されれば送信、拒否されれば承認カードが出る |
| 同じ宛先にもう一度送る | 前回「常に承認」を選んでいればルールに一致し、確認なしで送信する |
| 「常に承認」を選ぶ | ツール・操作・ワークスペースがルールとして保存され、次回から自動になる |
| ワークスペース外の元ファイルの不可逆な削除が必要になる | 毎回承認を求め、「常に承認」は出さない |
| 送金や証券取引をしようとする | ハードブロックとして実行しない（承認でも不可） |
| 離席中に自動判定が拒否する | その操作だけ保留し、再接続時にまとめて確認する。重複通知はしない |
| 設定に「外部送信は常に確認」と書く | 次回の自動判定がそのポリシーを参照し、送信前に確認カードを出す |

## 制約と検討事項

- 初期仕様では、ツールごとの権限エディタ、purpose / destination / data_kind の許可マトリクス、同意の版管理、可用性 API、独自ポリシー DSL、許可の有効期限管理を持ちません。設定はポリシーと常に承認の一覧だけです。
- 自動判定はモデルによる判断であり、単独の境界にはしません。sandbox、ハードブロック、承認、失敗時の拒否と組み合わせます。
- sandbox はホスト側の外部コード実行に限ります。sandbox が使えない環境では sandbox の外として扱い、自動判定と確認に回します。sandbox で実行したと偽りません。
- 端末内の操作は、端末の OS 権限と端末ごとの許可が境界です。ホストの sandbox／自動判定では代替できません。
- 外部ハーネス（ACP など）の実効範囲は、そのハーネスや OS が適用した範囲を表示します。ene が保証していないものを保証済みと表示しません。
- 接続経路のアクセス制御（Tailscale / Cloudflare など）は外部サービスへ委譲し、本機能とは別に管理します。
- 秘密情報はログ・記憶・通知へ残しません。
- 記憶や過去の行動、好みを根拠に、任された範囲が自動的に広がることはありません。
- 停止や解除の後も、完了済みのファイル変更や送信済みのトランザクションを自動的に巻き戻すことはできません。
- ルールとポリシーはコンパニオンごとに保存し、取り消しと監査を必ず提供します。
- ポリシーは簡潔な自由文とし、件数と長さに上限を設けます。秘密情報は書かせません。

実行の隔離・自動判定・承認の技術的な契約は[権限の設計](../../design/permissions.md)に定めます。過剰なマトリクス型 Grant（purpose/destination/data_kind）は完全に廃止され、`ApprovalRequest`（未決の承認要求）と `PolicyRule`（保存された常に承認ルール・ポリシー）に簡素化・一本化されています。
