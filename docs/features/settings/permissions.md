# 権限とデータの管理

コンパニオンは、許可された機能と任された権限の範囲内で、日常的な作業を自律的に進行します。ユーザーに細かな権限設定や過度な承認確認を求めることなく、新たなリソースへのアクセスや重要な判断が求められる局面でのみ、対話の中で自然に相談を持ちかけます。

[構想](../../vision.md)に掲げる「誰でも使える手軽さ」と「ユーザー主導のコントロール」を両立させ、現在利用中のサービスや操作対象を常に把握でき、任せる権限の変更や作業の停止をいつでも自由に行える環境を基本とします。

## 具体的な振る舞い

1. 日常会話、[記憶の抽出・整理・想起](../memory/README.md)、Web検索、専用作業領域での資料作成、任されたスケジュール実行などは、利用開始時に提示した範囲内で自律的に進めます。ファイルの読み取りや保存、ツールの個別呼び出しごとに承認を挟むことはなく、複雑な権限ルールの設定をユーザーに強いることもありません。
2. 外部サービスの連携や新機能の有効化を行う際には、対象となる操作、送信されるデータの種類・用途・送信先を簡潔に提示し、必要な権限をまとめて許可できるようにします。「指定フォルダ内での作業」「カレンダーの参照」「画面を見ながらのアシスト」といった機能単位でわかりやすく提示し、閲覧のみか編集を含むかといった判断に必要な要点を明示します。また、ホスト本体、操作対象の端末、外部クラウドサービスの所在も区別して扱います。
3. ユーザーからの明示的な指示や、継続的に任された役割において対象と操作があらかじめ定まっている場合は、その範囲内で再確認を行わずに実行します。自発的なアクションや定期実行にも同一の基準を適用します。なお、過去の行動や好みを記憶したことのみを根拠として、任された権限の範囲が自動的に拡張されることはありません。
4. 新たなリソースへのアクセスが必要な場合や、外部への送信先・公開範囲・課金や購入などに関する重要な判断が生じた場合は、実行前に対象と影響を明示して対話の中で相談します。単に「送信」「購入」といった操作名だけで一律に確認を挟むのではなく、事前の依頼や指示の文脈にその合意が含まれているかを適切に考慮します。ユーザーが「実行前に一度見せて」と明示した場合は、その指示を厳格に優先します。
5. 必要な相談事項はコンパニオンが対話形式に整理して伝えます。内部のツールやサブエージェントが個別に同一の承認を求めてくることはありません。ユーザーが離席中の場合は、判断を要する工程のみを保留とし、調査や下書きなど自立して進められる作業は継続します。結果と保留事項はホスト上に保持され、戻った際にまとめて報告されます。同じ保留事項を定期実行のたびに重複して通知することはありません。
6. 利用中のサービス、アクセス可能なフォルダ、端末機能は設定画面から一覧で確認でき、いつでも権限の変更や解除が可能です。作業の停止も即座に行え、進捗や実行履歴を後から透明に確認できます。アクセスの取り消しは、以降のすべての関連操作に即座に反映されます。
7. [ホストへの接続許可](../hosting/README.md)と、各クライアント端末内のファイルやツールへのアクセス権は厳格に分離して管理されます。端末機能を利用し始める際には、その端末で許可される範囲を明示します。ある端末で与えられた権限が別の端末へ自動的に波及することはなく、OSや外部サービス固有のアクセス権限確認にも適切に準拠します。

## 想定シナリオ

以下は期待される振る舞いの具体例です。前提として、必要なサービスや機能は利用開始時に提示された範囲内で利用可能であるものとします。

| シナリオ | 期待される振る舞い |
| --- | --- |
| 「この資料を整理して」と依頼する | 指定資料の読み取り、内容の整理、成果物の保存まで、個別の確認を挟まず自律的に完了する |
| 「毎朝、今日の予定を教えて」と依頼する | 連携済みのカレンダーを参照し、日々のスケジュール取得やユーザーへの通知を都度確認せず実行する |
| 「この文面をAさんに送って」と依頼する | 送信先とメッセージ内容が確定しており、送信機能の権限があれば、余計な再確認なしで送信する |
| コンパニオンが自発的に資料を新たな宛先へ送ろうとする | 任された権限の範囲外であるため、送信前に必ずユーザーへ相談する |
| 「整理して」という指示の過程で、元ファイルの不可逆な削除が必要になる | バックアップや退避を最優先とし、完全な削除が真に必要な場合にのみ事前に相談する |
| 不在時のスケジュール実行で新たな重要判断が発生する | 判断が必要な工程のみを保留し、作成できた中間成果物と保留事項を再接続時にまとめて報告する |
| 利用中の機能において、新たに画面情報のキャプチャ送信が必要になる | 当初説明したデータ送信の範囲外であれば、送信前にユーザーの明示的な許可を求める |

## 制約と検討事項

- 初期仕様においては、操作ごとの複雑な多段階ポリシーや承認ルールの手動エディタ、許可ごとの有効期限設定、独自のAI審査エンジンの搭載などは必須としません。利用機能のシンプルなオン・オフ管理、対話を通じた自然な相談、ワンクリックでの作業停止と履歴確認を軸とします。
- データ送信の許諾は、機能の利用開始時に提示したデータ種別と用途の範囲内に限定されます。許可されていない外部サービスへデータを不正に送信することは一切ありません。
- アクセス制限の実効性は、基盤となるハーネスやOSのサンドボックス機構に依存し、プロンプトによる指示（文章上の制約）のみに頼ることはしません。外部ツールやシェル環境に適用可能な制限を精査し、安全性が担保できない操作については利用開始時に明示します。
- ホストへの接続を解除された端末からは、以降そのホストの機能を利用できなくなります。同一ホストに繋がる別端末から相談に回答することは可能ですが、対象端末固有のアクセス制限やOSの制約を迂回することはできません。
- 作業の緊急停止や権限の解除を行っても、すでに完了したファイル変更や外部サービスへ送信済みのトランザクションを自動的に巻き戻すことはできません。

参考：[OpenClaw](../../references.md#openclaw)、[Hermes Agent](../../references.md#hermes-agent)、[nanobot](../../references.md#nanobot) のセルフホスト環境における自律実行とアクセス管理。既存製品の複雑な設定体系をそのまま持ち込まず、eneのシンプルなユーザー体験に合わせて最適化します。
