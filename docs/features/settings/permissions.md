# 権限とデータの管理

ユーザーに権限のことをほとんど意識させず、承認ダイアログすら極力出さないことを目標とします。**機械的な許可ルール → Decision API（安全確認＋自由文ポリシー判定）→ ユーザーの承認** の3段階で判定し、本当に必要なときだけ確認を求めます。

## 基本原則

1. **機械的な許可を最優先する**: ホスト管理の安全なツールや、ユーザーが「常に承認」として保存した操作ルールに一致するものは、確認なしで即座に実行します。
2. **Decision API による安全確認＋ポリシー判定**: 機械的ルールに一致しない操作は、自動判定（Decision API）へ回します。一般的な安全性に加えて、ユーザーが設定した自由文ポリシー（例:「外部への送信は常に確認」）に照らして問題がないかを評価し、問題なければ確認なしで実行します。
3. **ユーザー承認は最小限の最終段**: Decision API が危険またはポリシー違反と判断した場合にのみ、承認カードを提示します。ユーザーは **承認 / 常に承認 / 拒否** から選べます。
4. **「頭」を通じた自然な承認**: 画面の承認ボタンだけでなく、会話の中でユーザーが「いいよ」「進めて」と返答したと「頭」が判断した場合、「頭」が承認ツールを呼び出して代わりに承認を確定できます。
5. **失敗時は安全側**: Decision API がエラーやタイムアウトになった場合は、無断実行せずユーザー承認へ回します。
6. **秘密は渡さない**: APIキーなどの資格情報はエージェントに直接見せず、ホスト側の資格情報ストア経由でのみ利用します。

## 判定の流れ

| 段階 | 判定内容 | 結果 |
| :--- | :--- | :--- |
| **1. 機械的な許可** | ホスト管理ツール、または保存済みの「常に承認」ルールに一致 | そのまま実行 |
| **2. Decision API** | 操作内容・依頼文脈の安全性と、自由文ポリシーへの適合性を評価 | 問題なければ実行 / 要確認なら次へ |
| **3. ユーザー承認** | 画面カード提示、または「頭」による会話文脈からの代理承認 | 承認で実行（「常に承認」ならルール保存） |

## 具体的な振る舞い

1. ユーザーは設定画面で「自由文ポリシー」を追加・編集でき、保存された「常に承認」ルールの一覧確認・削除も行えます。
2. 「常に承認」が選ばれた操作はルールとして保存され、次回以降は第1段階の機械的許可で即座に通過します。
3. 離席中に要確認の操作が発生した場合は保留として保持され、戻った際の対話や画面からまとめて確認できます。
4. 実行履歴には判定結果と適用されたポリシー／ルールを記録し、あとから確認できます。

## 制約と検討事項

- OSネイティブのSandbox隔離は持ちません。`process-wrap`は子プロセスの起動・終了とプロセスグループの管理だけを行い、安全性は判定パイプラインと承認で担保します。
- ツールごとの複雑な権限マトリクス（purpose / destination / data_kind の組み合わせ設定等）は設けません。
- 秘密情報はログ・記憶・通知へ残しません。
