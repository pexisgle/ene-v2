# 自発的な働きかけ

ユーザーの作業状況や画面の様子をそっと見守り、直前の文脈やこれまでの記憶をふまえて、キャラクターから自発的に作業の提案や雑談を投げかけます。

## 具体的な振る舞い

1. 機能の利用開始時に、端末内で参照する情報の範囲や、クラウド利用時の送信先・データ種別・用途を明確に提示したうえで機能を有効化します。許可された範囲内で、対話用とは別の軽量・高速なモデルを活用し、ユーザーの作業状況や画面の変化、過去の記憶などを定期的に把握します。情報の取得や声かけのたびに確認ダイアログを挟むことはありません。
2. 収集したコンテキストに基づき、自発的に話しかけるべきタイミングかどうかを判断します。声かけの頻度や積極性は設定によって調整可能であり、気軽な雑談から作業に関する重要なリマインドまで柔軟に対応します。
3. **複数コンパニオン存在時の声かけ調停**:
   - 画面上に複数のコンパニオンが常駐している場合、キャラクターの性格や関係性によって見守り・声かけの基準はそれぞれ異なります。
   - 各コンパニオンは状況を考えたうえで、声をかけずに見守ることも選べます。複数のコンパニオンが声をかけようとする場合は、[ホストとクライアントの調停ルール](../hosting/README.md#複数コンパニオンの常駐と調停ルール)に従い、同時に発言することを避けます。
4. 話しかける話題や提案内容は、ユーザーの現在の状況や関心、過去の記憶を総合的に考慮して自然に決定されます。
5. 声かけに対するユーザーの返答後は、通常の[基本チャット](../chat/basic.md)と同様にスムーズな対話へと移行します。

## 制約と検討事項

- 状況の見守りは、コンパニオンが表示されているクライアント上でクライアントごとに独立して行われます。
- **画面解析とプライバシーの設計課題（検討中）**:
  - 画面状態の解析において、画面キャプチャをクラウド推論モデルへ定期送信する方式は、パスワードや機密情報、個人チャットが外部に漏洩する重大なプライバシーリスクを孕んでいます。
  - そのため、解析を端末内のローカル軽量モデル（ローカルVLMやOCR）で完結させるか、あるいはアクティブウィンドウのタイトルやアプリ名などの軽量メタデータのみを対象とするかなど、安全な画面情報取得アーキテクチャの具体化は今後の設計課題として継続検討します。
- 参照する情報の範囲や送信先を追加・変更する場合は、[権限とデータの管理](../settings/permissions.md)の方針に則り、変更前に必ず説明と同意確認を行います。ユーザーは端末単位で本機能を無効化できます。

参考：[Hermes Agent](../../research/references.md#hermes-agent) のスケジュール実行、および [Grok Bot](../../research/references.md#grok-bot) の継続タスク・通知機能。キャラクターからの能動的な声かけによる演出はene独自の提案です。
